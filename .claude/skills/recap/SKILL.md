# 收工盤點

四個問題，照順序回答：**做了什麼 → 使用者差在哪 → 該同步的同步了沒 → 進版控了沒**，
最後收斂成一段**結論**（寫在最後面，見 §4）。

**第四個是動手不是回答**：跑 `/recap` 就是授權 commit，不必再問一次（§3.5）。
`git push` 不在裡面——這是個公開 repo，推上去就是公開發表，那是使用者的決定。

這份 skill 的讀者是自己人。目的是讓「兩週後的自己」和「接手的人」看得懂發生過什麼，
而不是讓人覺得這段工作很厲害。**寫得像對帳單，不要寫得像捷報。**

**這個 repo 的特殊處境：worktree 是平行 session 共用的。** 隨時可能有另一個 agent
在同一棵樹上改別的功能。§0 和 §3.5 有一半的篇幅在處理這件事。

---

## 記號表（跨段落統一，一行只掛一個，掛在最前面）

盤點最常見的失敗是**每一條看起來都一樣可信**——「驗過的」「做好了但還沒生效」
「我猜的」混在同一串項目符號裡，讀的人只能逐句判斷。記號的用途是把那個判斷
**前置到行首**。

**狀態記號**——用在 §2 效益、§3 同步、§3.5 版控、「還沒做的」：

| 記號 | 意思 | 掛上去的條件 |
|---|---|---|
| ✅ | 做完且驗過 | **後面必須跟著證據**：數字、實測輸出、log 片段、截圖 |
| ⚠️ | 做完，但有已知限制或風險 | 限制要寫出來，不能只掛記號 |
| ⏳ | 做好了但還沒生效 | 要寫**卡在哪**（要重 build／要重開 app／等對方收尾） |
| 🔮 | 推測，沒有實測 | 「這樣應該會比較快」這類話一律掛這個 |
| ❌ | 缺口：該做／該同步但沒做 | §3 最重要的記號——那一節的讀者只在找這個 |
| ⚪ | 檢查過，確認不用動 | **要附一句為什麼不用動**，否則跟沒查一樣 |
| 🚫 | 不是這次的範圍／不是我動的 | 共用 worktree 常態：平行 session 的改動 |

**種類記號**——只用在 §1 做了什麼：

| 記號 | 種類 |
|---|---|
| ✨ | 新功能／新畫面 |
| 🔧 | 改既有行為 |
| 🎨 | **看得到的東西**：版面、動畫、顏色、吉祥物、瀏海 |
| ⚡ | 效能 |
| 🌐 | 介面文字與翻譯 |
| 🧪 | 測試 |
| 🧹 | 順手修掉的 |

### 五條紀律

1. **✅ 後面沒有證據就不是 ✅。** 這個 repo 的證據通常是三種：`./test.sh` 的數字、
   `~/Library/Logs/Clawdline.log` 的一行、離螢幕算出來的 PNG。拿不出來就降級成 🔮，
   或者老實寫「沒測」。**用記號取代證據，等於把宣稱偽裝成事實。**
2. **只承載「狀態」與「種類」，不承載重要性與情緒。** 禁用 🎉🔥🚀👍‼️⭐。
3. **沒有分類價值就不掛。** 標題不掛記號；散文段落、單句結論也不掛。
4. **一行只掛一個。**
5. **§4 結論整段不掛記號。** 那一段是判斷不是清單。

## 0. 先蒐證，再下筆

不要憑對話印象總結——印象會把「打算做」記成「做了」。動筆前先取事實：

```bash
git log --oneline -15                    # 這段工作的 commit
git status --short                       # 還沒進版控的東西
./test.sh 2>&1 | tail -3                 # 測試總數現值（不要引用上次記得的數字）
```

**分清楚哪些是自己的。** working tree 幾乎一定有平行 agent 的未提交變更。
不確定就 `git log --oneline -3 <檔案>` 查那個檔最近是誰動的。

**而且要反過來查一次**：`HEAD` 還是不是開工時那一個？我改的檔有沒有已經被別人
commit 走了？兩件都會發生，而它們決定 §3.5 要怎麼下手。

**測試數要現跑。** README 和 CONTRIBUTING 兩處都寫著數字，而 `test.sh` 自己會比對——
數字對不上它會擋下來，所以這不是可選的。

## 1. 做了什麼

按「使用者看得到的東西」分組，不要按檔案分組。每一項要能回答「這是什麼、在哪裡」：

- ✨ 新功能：怎麼觸發（哪個鍵、選單哪一項）＋ 一句它解決什麼
- 🔧 改到既有的：改了哪個行為、為什麼
- 🎨 看得到的東西：**這一類要附圖**。版面、動畫、顏色用文字描述沒有意義，
  而這個 repo 有離螢幕算圖的路（`clawdline://snapshot`，含 `island=` 與 `list=`），
  不需要錄影權限
- ⚡ 效能：**要有前後數字**。「比較快」不是一條盤點，「443ms → 86ms」才是
- 🌐 介面文字：加了幾個字串、幾種語言、哪些是刻意不翻的
- 🧪 測試：新增幾個、全套跑過沒

**🧹「順手修掉的」單獨列一段。** 這些最容易在總結時蒸發，但常常是後續最省時間的
部分。修 bug 的那幾條要寫**當初為什麼會錯**——那是下一個人唯一用得上的部分。

---

## 2. 使用者差在哪

分兩堆寫，**不要混在一起**。這一節的記號承載的是**真實性**。

### 可驗證的
有數字、有實測、現在就能看到的。每一條要附證據：

- ✅「切換 session 從 443ms 降到 86ms，四個階段各自量過」← 這是效益
- 🔮「面板變順了」← 這是宣稱，要配上面那行才算數
- ⚠️「量的是這台機器上的一份 29MB transcript，小專案不會有這個差距」← 有限制就寫

**動工前 vs 現在的對照用表格。** 表格裡不掛記號——欄位本身就是分類。

### 還沒兌現的
做好了但使用者還看不到的，⏳ 並講清楚卡在哪：

- ⏳「改了但還沒 `./build.sh`——現在跑的還是舊的 app」
- ⏳「要重開 Clawdline 才會生效」

**「進版控了」與「跑起來看得到」是兩件事。** 這個 repo 沒有 CI 部署，
所以反過來要小心的是：**commit 了不代表你電腦上跑的那個 app 是新的**。
`./build.sh` 沒跑就是沒跑。

## 2.5 動到看得見的東西就要自己看一眼

**這一節在「同步」前面，因為它管的是「這次改動到底對不對」。**

改到版面、動畫、顏色、瀏海、吉祥物——`./test.sh` 全綠不代表它長得對。
測試驗的是解析與算術，**刻意不驗任何需要視窗的東西**（Tests/main.swift 開頭就寫了）。

這個 repo 有三條不需要任何權限的自我驗證路，收工前至少走一條：

```bash
# 面板（含 ⌘K 清單、⌘J 讀取面板）
open "clawdline://snapshot?path=/tmp/x.png&list=sessions&output=1"

# 瀏海的四種狀態
open "clawdline://snapshot?path=/tmp/i.png&island=waiting"   # working|working2|waiting|finished

# 它到底有沒有出現在該出現的地方
grep "island:" ~/Library/Logs/Clawdline.log | tail -3
```

**`screencapture` 沒有錄影權限時會回一張「桌布＋所有視窗被剝掉」的圖**，
看起來像是東西沒畫出來。要拍實機請使用者拍，不要自己下結論說沒畫。

**log 是這個 repo 最被低估的證據。** 「視窗在不在該在的位置」「層級是多少」
這種問題，肉眼看不出來而 log 一行就講完——2026-08-18 那次 `level=3` 就是這樣抓到的
（`isFloatingPanel = true` 會把先前設的 level 洗掉）。

## 3. 該同步的同步了沒

逐項對照，產出**缺什麼**的清單，不是「都好了」的自我肯定。逐項掛狀態記號——
讀者真正想知道的只有一件事：**哪幾格是 ❌。**

### 3.1 翻譯——加了給人看的字就要有十四種

**這是這個 repo 最容易漏、而且漏了最不容易發現的一件事**，因為漏掉的那一半
只有讀那個語言的人看得到。所以它排在第一。

編譯器只擋「少實作一個」（protocol 的功勞）。它擋不掉**照抄英文**，
也擋不掉**根本沒進 `Copy` 而是寫死在 Swift 裡**的字。這兩種要自己查：

```bash
# 1. 有沒有新字串，而某些語言只是照抄英文
./test.sh 2>&1 | grep -E "still English|implements every string"
```

`Tests/main.swift` 的「the languages the interface speaks」那組會用 `Mirror`
掃**每一個** stored string 去比對，不是抽驗——所以新加的字串會自己帶著檢查進來。
真的同字（西班牙文的 "General"、義大利文的 "output"）在那裡用 `tag:member` 逐項豁免，
**不要用全域豁免**：「log」在義大利文是那個字，不構成中文也可以是那個字的理由。

```bash
# 2. 有沒有寫死在程式裡、根本沒經過 L.t 的介面文字
git diff --name-only HEAD | grep '^Sources/.*\.swift$' | while read f; do
  grep -n '"[^"]\{3,\}"' "$f" | grep -v 'L\.t\.' | grep -v '^\s*[0-9]*:\s*//'
done
```

第二個會有雜訊（識別字、格式字串、bundle id、字型名），**要逐條看，不要看數字**。
判準是一句話：**這個字會出現在使用者眼前嗎**。會 → 進 `Copy`。

| 情況 | 做什麼 |
|---|---|
| 加了新的介面文字 | `Sources/Strings.swift` 加成員 → 十三個 `Copy+*.swift` 都補（中文那個檔有兩個 struct） |
| 那個字在某語言真的同字 | 到測試的 `sameIsFine` 加一條 `tag:member`，**附一句為什麼** |
| 專有名詞（Whisper、Apple、bundle id、字型名） | 不進 `Copy`，維持原文 |
| 單位（秒、pt、%） | 秒要進 `Copy`（`settingsSeconds`），pt 和 % 不用 |

**不會講的語言就照著現有檔案的水準寫，然後在報告裡講出來哪幾種沒把握。**
README 本來就寫著歡迎糾正——但那句話的前提是東西有寫進去。

### 3.2 兩份 README 要一起改

`README.md` 和 `README.zh-TW.md` 是**兩份平行的文件，不是翻譯**。動了其中一份講的
行為，另一份就過期了，而沒有任何東西會紅。

```bash
git diff --name-only HEAD | grep README
```

只出現一個 → ❌，除非有理由（例如只改了英文的錯字）。

同一條也適用於：`CONTRIBUTING.md` 的測試數、`docs/` 底下被改到行為的那幾頁。

### 3.3 測試數是被檢查的

`test.sh` 最後會拿 README 裡寫的數字跟這次跑出來的比，不一樣就 exit 1。
所以**加了測試就要改三個地方**：`README.md`、`README.zh-TW.md`、`CONTRIBUTING.md`。

### 3.4 其他該看的

| 該檢查的 | 什麼情況下必須動 |
|---|---|
| `README.md` ＋ `README.zh-TW.md` | 行為變了、加了設定、加了鍵 |
| 設定檔區塊（兩份 README 都有） | `Config` 加了 key |
| `CONTRIBUTING.md` | 測試數變了、開發流程變了 |
| `docs/compatibility.md` | 動了 `Sources/Compat.swift`——它是產生的，`tools/build-compatibility.py --check` 在 `test.sh` 裡把關 |
| `docs/project-status.md`／`docs/devstack.md` | 動了讀取那些檔案的格式 |
| `docs/mascots.md` | 動了 mascot pack 的格式 |
| `.claude/skills/*/SKILL.md` | skill 描述的行為變了 |
| memory（`~/.claude/projects/.../memory/`） | 非程式碼可推導的決策、踩過的坑 |

⚪ 那一格**必須附一句為什麼不用動**。「這輪沒動任何 `Config` 的 key，也沒加鍵」
是合格的；只寫「⚪ 不用動」等於沒查。

## 3.5 把這批東西 commit 進去——**收工的一部分，不是選項**

**跑 `/recap` 就是授權 commit。** 不必再問一次。**但只 commit，不 push。**

### 先綠再 commit

```bash
./test.sh                                # 不要接 pipe，見下
```

**不准把要當判準的指令接進 pipe**：`./test.sh | tail -3` 的 exit code 是 `tail` 的，
永遠是 0——**測試紅了照樣 commit，而且畫面上還印著「全綠」**。要看尾巴就分兩次跑。

紅了怎麼辦，看是誰的：

| 紅的是 | 做什麼 |
|---|---|
| 我這批造成的 | 修完再 commit |
| **別人未提交的改動造成的** | 照樣 commit 我自己那幾個檔，**但報告裡要講**紅在誰的東西上 |
| HEAD 本來就紅 | 順手修掉，跟自己的東西一起 commit，列進「順手修掉的」 |

**`input file '…' was modified during the build` 不是紅，是撞車。** 平行 session
正在寫檔。等一下重跑，不要去改對方的檔。

### 三種狀態，做法不同

| 查到什麼 | 做什麼 |
|---|---|
| 我的東西全部未提交 | 照下面的做法 commit。這是常態 |
| **HEAD 動了，而且不是我推的** | 照樣 commit，但報告裡講出來 |
| **我的一部分被別人 commit 走了** | **先看那半進去了什麼**，再補上缺的那半 |

### 怎麼 commit

**逐檔指名，不准 `-a`、不准 `.`、不准 `git add -A`。** 共用 worktree 裡這三個
都會把別人做到一半、剛好存了檔的東西一起帶走。

```bash
git status --short                       # 逐項確認哪些是我的
git status --short | grep -E '^[MARCD]'  # 已經在 index 裡的（別人先 add 過的）
git add <路徑> <路徑> …                    # 一個一個列
git diff --cached --stat                 # commit 之前看一眼真正會進去的是什麼
git commit -m "…"
```

**先看 `git status --short` 的第一欄。** 那一欄是 index。平行 session 如果先
`git add` 過它自己的東西，我的 `git commit` 會把它們一起提交，而我一個都沒指名。
發現多了別人的東西**不要 `git reset` 踢掉**——那會清掉對方刻意 stage 的狀態。
照樣提交，然後在報告裡講清楚哪幾個不是我的。

**別 `git stash`**：平行 session 會在那個空檔把 staged 的東西 commit 走。

### 拆成幾個

判準跟 §1 同一條線——**使用者看得到的東西**：

> 這批如果要 revert，有沒有可能只想 revert 其中一半？有 → 拆開。

一次工作通常是二到四個。這個 repo 的訊息格式看 `git log --oneline -15`：
`type: 一句話講改了什麼——破折號後面接為什麼`。**主詞是行為不是檔案**：
「tmux 完全偵測不到 claude，因為安裝器的 symlink 蓋住了名字」看得懂，
「修改 Tmux.swift」看不懂。

### 為什麼不 push

**這是個公開 repo。** commit 是「把工作存好」，隨時改得掉；
push 是「公開發表」，而且 CI 會在那時候跑起來。那是使用者的決定。

所以收工報告的最後要留一句：這幾個 commit 還沒 push，要不要現在推。

## 4. 結論——**放最後面，也最後才寫**

對帳單的問題是：每一行都對，讀完卻不知道「所以呢」。這一段補那一句。

**放在最後面**，因為讀者需要先看過證據才看得懂判斷。動筆順序也是最後——
先寫結論再湊證據，寫出來的會是感想。

### 四件事，每件一到三句

| | 要回答什麼 |
|---|---|
| **淨結果** | 這段工作結束時，**這個 app 跟開始前差在哪**。一句話，不是清單 |
| **能不能出** | 現在這棵樹 build 得起來、測試綠嗎？不能的話**卡在哪一件具體的事** |
| **下一件** | 最該接的**一件**（不是三件）。為什麼是它 |
| **哪裡沒把握** | 沒測的、只有一組觀察的、靠推測的、翻譯不會講的那幾種 |

### 三條紅線

1. **結論是判斷，不是摘要。** 可以由上面幾段機械推導出來的不是結論，是目錄。
2. **「能不能出」要給答案，不要給選項。**
3. **不確定要標明程度，而且要標在結論裡。** 讀者是讀到這一段才做決定的。

反例（這樣寫等於沒寫）：「這次修了三個問題，測試都綠了，文件也補了。」
——那三句在下面都有，而且它沒有回答任何一個「所以呢」。

## 輸出格式

```
1 做了什麼
2 使用者差在哪   可驗證的 vs 還沒兌現的，分開寫
2.5 自己看過了嗎  動到看得見的東西就要，沒看要明講
3 同步了沒       翻譯（§3.1）／兩份 README（§3.2）／測試數（§3.3）／其他（§3.4）
3.5 進版控了     這次 commit 了哪幾筆、什麼留在 working tree、還沒 push
還沒做的
卡在你身上的（有才寫）
```
