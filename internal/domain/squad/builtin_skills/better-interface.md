# Interface review

Use this skill when reviewing a whole web screen, flow or interface across accessibility, layout, copy, typography, colour and polish and returning one ranked report with a Block or Approve verdict; not for writing new UI.

Report evidence, not taste. A density, radius or voice you merely disagree with is not a finding; a deliberate project choice is left alone.

1. **Resolve the scope.** Name the screen, flow or feature, including its empty, loading, error and narrow-width states. If the scope is too large to inspect credibly, narrow it to one complete flow, say what was excluded, and never imply uninspected surfaces were reviewed. For a branch or diff, review only what the task names.
2. **Recon.** Identify the framework, styling system, component library, tokens, supported viewports and the project's preview or test commands. Read what the project says about its interface (contributing and agent instructions, design-system docs). A documented convention settles taste, never an escalation trigger; when a shared token or guideline causes a problem, report it once at that source.
3. **Review each domain** in order: accessibility, layout, copy, typography, colour, polish and motion. Use the rules of the other Skills this role carries for their domains, and the project's own rules. A domain with no source of rules you actually applied is marked `Not reviewed`, not `Clear`.
4. **Verify.** Run the safe checks the project offers and inspect the rendered interface where runtime or visual judgement matters. A check you cannot run is `Not verified`, never a finding. A visual finding needs the rendered state; a code finding needs `path:line` and the current code.
5. **Severity.** `HIGH` blocks a task, misleads, hides content or controls, risks data loss or is a repeated systemic failure. `MEDIUM` harms comprehension, efficiency, adaptability or consistency. `LOW` is isolated polish. These are `HIGH` on sight however minor the surface: a control with no accessible name; no visible focus indicator; a pointer path with no keyboard path; motion that ignores reduced motion; content clipped or unreachable at 320px width or 200% zoom; failing text contrast; meaning carried by colour alone; a destructive action with no confirmation, undo or distinct treatment; truncation with no way to the full value; content past a scroll edge or disclosure with no visible cue; an error that names no way to recover; a semantic colour used against its meaning; a state change carried only by motion.
6. **Prefer the cheaper fix**, in this order: delete, use the platform's native element, reuse a project token or component, correct the value, and only then add something new.
7. **Consolidate.** One root cause is one row listing every location; rank by severity, then by how much one fix reaches. At most 15 findings; triggers first, and say how many the cap left out. A short report is fine.

**Output.** Scope and coverage table (domain, evidence inspected, findings count or `Clear` or `Not reviewed` with reason); one findings table (severity, domain, location, before, after, why); verification steps and results; then `Block` if any `HIGH` remains, else `Approve`, naming every domain not reviewed. A review is read-only unless the task also asks you to apply the fixes.
