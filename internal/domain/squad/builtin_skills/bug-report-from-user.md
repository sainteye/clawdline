# Bug report from a user's words

Use this skill when a person describes a problem in their own words (a message, ticket, email, or chat) and it needs to become a report someone can reproduce and fix.

1. Reduce the description to four parts: trigger (what they did), expected (what they thought would happen), actual (what happened), and surface (where: screen or URL, version, device, operating system).
2. Mark every part the description does not supply as a follow-up question. Do not fill it with a guess.
3. Write a one-sentence headline from the person's point of view, the steps, expected, actual, and surface.
4. State confidence: high when the report reproduces on its own, medium when one or two assumptions were needed, low when it needs significant guessing. List each assumption.

Describe symptoms, not a guessed root cause. Do not assign severity without evidence, and do not promise a fix or a timeline. A subjective complaint without a measurable claim is a usability or performance question, and a request for something new is a feature request; say which. The result is a draft: do not send a reply or file it in a tracker unless the task authorizes that.
