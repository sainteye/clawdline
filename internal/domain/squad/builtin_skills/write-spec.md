# Evidence-based product specification

Use this skill when turning a user problem into a Feature, Issue, or implementation specification. Read the owning Board item, code path, prior decisions, and any available usage evidence before writing requirements.

1. State who is affected, what they cannot do, and the observed evidence. Distinguish facts from assumptions and record unknowns.
2. Describe the journey and scope in user terms. Name at least one smaller alternative and the trade-off behind the chosen scope.
3. Write acceptance criteria that can be verified with a command, test, API response, or specific review artifact. Cover failure, permissions, and existing behavior where relevant.
4. Record dependencies, non-goals, and decisions in the owning Clawdline Board item. Keep implementation choices open until the responsible engineer has examined the code.

Do not assume connected research tools, invent metrics, or treat a candidate source as adopted without review.
