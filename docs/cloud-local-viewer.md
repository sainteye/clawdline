# Local CLI viewer authorization

## Local viewer boundary

A local daemon page is built with `DoorGate` (`web/console/src/main.tsx`). The hosted page is built with `CloudGate` and is usable only at its declared `appOrigin`. `CloudViewerSession` (`web/console/src/legacy/js/net/cloud-boot.js`) obtains an httpOnly session cookie at the Cloud API origin and keeps its nonextractable Ed25519 key in that origin's IndexedDB. The Cloud API CORS allowlist contains the hosted app and marketing origins, while its login and session cookies are `SameSite=Lax`. A localhost page cannot borrow that viewer principal. `clawdline cloud login` registers a *machine*, and the Cloud service's machine credential must not become a viewer credential by account-ID equality.

This branch adds `clawdline cloud viewer login|status|machines|pair` as a distinct authorization and encrypted handover client. Against a Cloud API that does not yet support viewer device authorization, `login` returns `viewer_flow_unavailable`, saves no key or credential and exposes no machine-role fallback. Pairing requires the selected machine ID and fingerprint, prints a one-time offer for `clawdline cloud pair --offer`, authenticates the ciphertext against that machine's roster key, and stores its content key in an owner-only local pin.

The daemon owns one viewer relay line for the Agent CLI. `/v1/cloud/viewer/{status,machines,sessions,detail,actions,receipts}` accepts only the daemon's **own local device token** through DoorGate. A paired remote browser or a local browser signed in with a separate read/send device cannot borrow this viewer. The separate local Console Cloud Sessions page has been removed; the hosted CloudGate shows multiple machines in the existing Session page with its own browser-origin viewer. The CLI still uses the daemon's viewer line. Logging in or pairing from the CLI takes effect on the daemon's next viewer request without a daemon restart. Turning Cloud on still follows the existing machine-line restart behavior.

For each `r/` detail read, the daemon records the selected machine, Session, execution generation, read name and request envelope sequence. It accepts a decrypted `t/` reply only when all five echoed fields match. A relay realignment's retained `t/` answer is discarded; retained `ss/` and `s/` rows remain available for a fresh status or detail read. A missing or mismatched echo returns `read_reply_mismatch` and never exposes the old body as current content.

The first detail read returns the newest 200 transcript entries and an optional `next_before` byte cursor. A person requests one older page with `clawdline cloud viewer read --machine MACHINE_ID --session SESSION_ID --generation GENERATION --before CURSOR`. Each page uses `r/<machine>` with the exact `transcript.before.<cursor>` read name, the same three-part target and a new request sequence. The daemon checks the current `ss/` projection before and after every page and accepts no reply lacking the matching proof. It never preloads the full history. An absent `next_before` means the beginning of the record was reached.

The local viewer only sends when the Cloud switch is on, an explicitly authorized viewer identity exists, and the selected machine has a fingerprint-checked encrypted handover. Before each use, the daemon rechecks the account roster and removes a revoked or changed pin from active use. It does not queue an offline action.

This source branch is not production acceptance by itself. The private Cloud API viewer-device extension, exact-capability relay and new `ss/r` machine wire must be integrated and deployed in the safe order described below, then exercised together.

## Person-facing flow

On the local machine, turn Cloud on if needed and authorize the separate viewer identity. The displayed approval page names the device key and exact requested capabilities. Then list registered machines, compare the target's fingerprint with its own screen, and hand over the pairing offer there:

```text
clawdline cloud on
clawdline cloud viewer login
clawdline cloud viewer machines
clawdline cloud viewer pair --machine MACHINE_ID --fingerprint FINGERPRINT
# On the selected machine, run the clawdline cloud pair --offer command printed above.
clawdline cloud viewer sessions
```

`sessions` prints every visible machine's state, including unpaired, offline, stale and incomplete projections. It never represents an absent retained row as an empty list. An optional `--machine ID` limits the list. Every actionable row prints its machine ID, Session ID and 32-character execution generation. These exact values are required for reads and actions:

```text
clawdline cloud viewer read --machine MACHINE_ID --session SESSION_ID --generation GENERATION
clawdline cloud viewer read --machine MACHINE_ID --session SESSION_ID --generation GENERATION --before NEXT_BEFORE
clawdline cloud viewer send --machine MACHINE_ID --session SESSION_ID --generation GENERATION --text 'Message'
clawdline cloud viewer receipt --machine MACHINE_ID --session SESSION_ID --generation GENERATION --action send --request REQUEST_ID
```

Read output includes `next_before` when another older page is available. Pass that value to the next `read --before`; keep the same machine, Session and generation.

The CLI prints the request ID **before** submitting a mutation. If the reply is lost or the relay disconnects, the command reports uncertainty and prints the receipt lookup command. A read-only receipt lookup never resends an action. A receipt for an older execution remains queryable after the Session's generation changes, provided the viewer still has permission to reach that machine. The hosted Console's existing Session page presents the per-machine projection and pinned detail; its detail URL is `#machine=<encoded>&session=<encoded>&generation=<32-lower-hex>`.

## Minimum Cloud API extension

Extend the existing RFC 8628 `/v1/auth/device/start`, `/v1/auth/device/approve`, `/v1/auth/device/poll` records with a discriminated `kind: "viewer"`. The machine shape and its existing behavior stay separate.

1. `POST /v1/auth/device/start` with `{kind:"viewer",name,public_key,caps?}` accepts an Ed25519 public key and returns the existing `device_code`, `user_code`, `verification_uri_complete`, `expires_in`, `interval`. It rejects unknown fields, invalid keys and `terminal_control`. Omitted `caps` requests read, transcript, prompt and start capabilities; an explicit read-only grant may contain only `read_sessions` and `read_transcript`. It stores a hash of `device_code`, the immutable viewer public key, its name, exact caps, expiry and poll interval. Neither an account nor a machine ID comes from the caller. A server lacking the extension returns `bad_machine` or `unsupported_device_kind`; the CLI maps that to `viewer_flow_unavailable`.
2. At the existing `/connect` page, a signed-in person uses `POST /v1/auth/device/preview` to see **CLI viewer device**, its name, key fingerprint, exact capabilities, expiry and a `review_digest`. The page shows each capability and expressly approves or denies the request. Approval for a viewer requires `expected_kind:"viewer"` and the previewed `review_digest`; a mismatch refuses without consuming the code. The digest binds the pending code record, kind, public key, name, capabilities and expiry and is compared inside the approval transaction. Approval creates or reuses a `web_devices` row for that exact public key and exact capabilities, subject to viewer-device quota. Reusing the key with changed capabilities is refused. It never creates a `machines` row. Code approval is single-use and expires. The browser's hosted cookie or fresh login ticket is used only on that origin; it is not sent to localhost.
3. `POST /v1/auth/device/poll` with `{device_code}` retains `authorization_pending`, `slow_down`, `access_denied` and `expired_token`. On success it returns `{status:"complete",account_id,viewer_device_id,viewer_credential}`. It must never return `machine_id` or `machine_credential` for a viewer request. The credential is produced reproducibly for an exact reply-loss retry during the unexpired code lifetime, stored only as a hash, and scoped to that viewer row. Cross-kind replay fails. Polling after expiry or revocation cannot resurrect the credential.
4. `/v1/tokens/device` accepts the viewer credential as a separate authenticated principal, checks the current viewer row, key/capability epochs and account revocation epoch, then mints a short-lived token with `role=viewer`, `sub=viewer_device_id`, identity/key/capability epochs, key fingerprint, JWKS generation and the row's exact public key/capabilities. A read-only grant never gains `send_prompt` at token issuance. Machine credentials keep `role=machine`; a machine token cannot enumerate or act as another machine's viewer. The relay's signature challenge proves possession of the viewer private key. A copied bearer credential alone must not enable reading ciphertext or signing commands. The exact-capability relay must deploy before the new API begins issuing viewer credentials.
5. The CLI stores its separate signing seed in `cloud/viewer-ed25519-v1`, identity in `cloud/viewer-identity-v1.json`, and authenticated per-machine handovers in `cloud/viewer-machine-pins-v1.json`, under the app's owner-only state directory. It prints only the human approval code, safe URL, device ID, fingerprints and one-time pairing offer; credentials and content keys are never printed. A missing or unreadable identity is a refusal, never an instruction to register under the machine key. `status` does not assert that any machine is paired or online. The daemon alone signs viewer relay envelopes, using a sender-specific durable sequence fence, so concurrent CLI and Console requests never race one signing sequence.

The Cloud extension must expose typed `unsupported_device_kind`, `device_limit_reached`, `access_denied`, `expired_token`, `revoked`, `capability_denied` and `bad_key` errors as applicable. It must enforce a bounded request/poll rate and return its `slow_down` interval. It must not add localhost to CORS, loosen cookie `SameSite`, export hosted browser keys, or mint a viewer token from a machine credential. The CLI talks to the configured HTTPS API directly for login and pairing, without browser cookies. The local daemon holds the explicitly approved viewer device credential; its HTTP endpoints remain behind the local door.

The private viewer implementation also changes `marketing/marketing-claude/src/pages/connect.astro`. Its hosted `/connect` page posts the code to `POST /v1/auth/device/preview`, displays the viewer kind, key fingerprint and each exact capability, then sends `user_code`, `expected_kind` and the preview's `review_digest` to `POST /v1/auth/device/approve`. Production viewer approval is not ready until this marketing page is deployed with the API routes and verified in a browser. Deploy the relay with exact viewer capabilities first; only then enable the API's new viewer credential issuance. An integrated rollout must verify that the preview and approval use the same digest, changed or expired codes are refused, and a successful viewer still needs an explicit per-machine encrypted pairing before reading content. This branch has local tests for the private routes and marketing build, not a production browser approval trace.

## Pairing and encrypted reads

Authorization is only the first gate. The CLI viewer must explicitly pair with **each** target machine using the existing `/v1/pairing/start` → machine `clawdline cloud pair --offer` → `/v1/pairing/claim` handover (or the QR invitation variant once viewer bearer auth is admitted to `/v1/pairing/invitations/accept`). The Cloud API must accept the new viewer principal on those pairing routes while retaining exact account, claimant and device-ID checks. The handover carries the machine's signed public key and content secret encrypted for the viewer's ephemeral key. The client verifies the machine fingerprint with the person, pins the machine key and stores the content key per machine. The account's device roster and Cloud token alone provide neither the key nor permission to infer pairing. Local or account revocation removes route eligibility immediately; any saved decrypted snapshot must become unavailable. A replacement machine key requires a fresh explicit pairing.

After pairing, the CLI viewer and hosted Console follow the same Cloud wire contract while holding separate viewer identities and keys. The Cloud Console exports `SessionDestination {machineID,sessionID,executionGeneration}`, `destinationKey` / fragment parsing, `ProjectedSession`, `MachineSessionProjection`, and `statusSource(current CloudClient)`; its `readMachine` reads only `ss/`, and `readDetail` checks the projection and generation before subscribing to `s/` and `t/`. Keep hosted URL targets as `#machine=<encoded>&session=<encoded>&generation=<32-lower-hex>`. A CLI request names all three values explicitly. Read, command, cache and receipt IDs must include the same triple. Refuse missing or changed generations rather than use a session ID alone. A refusal is not a dead end: an assistant that restarts keeps its terminal id and takes a new generation, so a viewer must be able to name the row that replaced the one a person opened and offer it as an explicit press. That replacement comes from a fresh complete status reading, as a whole three-part destination with `freshness: "current"`, and only when exactly one row matches that machine and Session; it is read exactly as any other opened row. A viewer must also tell apart a machine that published `machine.read_content_v1` as absent from one whose capability it has not read or whose reading expired, and must not call the second an old machine. Query current per-machine capability, grant and freshness before action; offline means refusal, never deferred delivery. For mutations, the single idempotency key and the machine's persistent receipt from the persistent-receipt branch bind the viewer, destination, action and request ID; uncertain results are queried, never blindly replayed. Relay accepted, machine executed, result delivered, viewer observed and person acknowledged remain separate states.

## Verification required for integration

- Old Cloud API returns `viewer_flow_unavailable`; no key or credential is saved and no machine credential is tried.
- A viewer code must visibly identify a viewer, and approval registers one `web_devices` row with the exact submitted public key; denial, expiry, quota and code replay are typed. Lost poll response cannot create a second device or issue a different credential.
- A stolen viewer bearer without its signing key fails relay admission; a machine credential fails viewer-token minting. Revocation and key/capability epoch changes invalidate minting and routing.
- Viewer login stores owner-only files, prints no credential or token, and never changes the machine key or identity. A corrupted identity, mismatched API origin, or missing key fails closed.
- Pairing with machine A does not grant B. Two machines with the same Session ID remain distinct. A renewed execution generation rejects old detail URLs, commands and receipt lookups. Permission and capability failures are typed; an offline machine never queues an action.
- A lost action reply leaves an uncertain receipt; lookup uses the same key and triple, distinguishes accepted from executed, and never resends merely because the viewer timed out.
- CLI tests cover the local daemon viewer; browser automation covers the hosted CloudGate. No localhost cookie, CORS exception or same-account shortcut is used. Production acceptance needs the integrated Cloud API, relay, machine and viewer candidate plus its deployment evidence.
