# Persona skill candidate decisions

Use this reference when you design the persona squad's skill list. It gives each of the 42 adapted built-in personas one bounded-task candidate and a separate decision about whether the pinned text was ready for **manual preview** during the research cycle. The [machine-readable ledger](persona-skill-decisions.json) preserves that research snapshot, including the exact source, commit, file hash, license evidence, referenced-file audit, fit, and limit for each candidate.

After the person explicitly requested integration on 2026-09-29, the 11 preview-ready candidates were reviewed against the current role manuals and repository rules, then adapted into [bundled skill content](../internal/domain/squad/builtin_skills/) and [versioned catalog entries](../internal/domain/squad/builtin_skills.go). Their roles are backend, frontend, technical-writer, product-manager, ux-researcher, accessibility, sre, devops, incident-commander, finops, and ui-designer. A later review of [Matt Pocock's pinned `code-review` skill](https://github.com/mattpocock/skills/blob/c55ee46073ed923f86ce59a5eb3b6d895095d1b7/skills/engineering/code-review/SKILL.md) added one bounded two-axis skill for `code-reviewer`. A 2026-10-02 round, described [below](#2026-10-02-four-public-skill-collections), added 11 more, and an [original skill](#original-skills) came with the `zero-review-lead` persona; the current catalog has 24 roles with one skill each and 19 with zero. These are local, portable adaptations for the repository in which a Session actually works, not provider skill installations or live network dependencies. Previous bundled texts remain in [version history](../internal/domain/squad/builtin_skill_history/) so pinned Project choices still resolve. The research ledger's `adoption: unverified` describes its earlier snapshot and is intentionally not rewritten as a claim about these later releases.

The `code-reviewer` adaptation retains separate checks for project rules and requested behavior, while the role manual still determines severity and evidence format. It does not install upstream setup tooling, create issue-tracker entries, publish comments, or require parallel agents. The pinned source is MIT licensed; the [copyright and permission notice](licenses/mattpocock-skills-MIT.txt) is bundled. The other candidates from this upstream repository remain research only.

Manual preview in this ledger means a person could read the pinned entry and the reviewed bundled references. It did **not** itself authorize adoption or prove provider execution. The later adoption described above is backed by the bundled content, catalog references, and launch-snapshot tests. For a persona with no preview-ready candidate, render zero skills. Keep its partial-fit research candidate visible only in the decision ledger until the remaining review is done.

## How the review was bounded

The earlier two research rounds supplied candidate leads. The more specific second-round finding takes precedence for the 14 personas it revisited. Every retained candidate here has a full upstream commit, a pinned original SKILL.md, its SHA-256, and a pinned applicable license file with its SHA-256. All 42 entries and 18 license sources were fetched and screened without installing or executing their content. Repository popularity was not a decision criterion.

This table and the next paragraph describe the first two rounds. The 2026-10-02 round added 12 more preview-ready candidates, listed in [its own section](#2026-10-02-four-public-skill-collections), so the ledger now holds 23; the self-test below counts all of them.

For the first two rounds' 11 manual-preview candidates, the audit followed local Markdown links and bundled reference paths recursively from the pinned entry. Every visited file is listed with a pinned URL, digest, and read-only review outcome. External links, live services, sample commands, and scripts are excluded from the preview. A preview candidate whose referenced file is omitted fails the upstream closure check. The other 31 candidates retain a bounded fit finding and an open reference audit; their preview decision is blocked with a reason. A bounded fit is not a claim that the skill can take over the whole persona. In particular, the trend, customer-success, and privacy candidates leave core role duties uncovered.

Run the local check from the repository root:

```text
python3 tools/check-persona-skill-decisions.py --self-test
43/43 personas; 54 pinned candidates; 23 manual previews; 1 original skills; 0 upstream file reads; valid
```

The self-test changes the ID order, removes and duplicates an ID, floats a source URL, mismatches license evidence, falsely marks an open audit as preview-ready, drops the original skill from the ledger, and points it at a file that does not exist. To recheck the pinned public files and recursive bundle closure, run `python3 tools/check-persona-skill-decisions.py --self-test --verify-upstream`. On 2026-09-29 this read 74 unique upstream files and passed; on 2026-10-02, with the third round, it read 102. The check also requires every skill in the built-in catalog to be a reviewed candidate of its role, which the ledger had not satisfied for `code-reviewer` until that round, and it ignores links inside fenced examples, which name no file. The online check uses public GitHub file URLs; it does not call a usage-priced API or execute third-party code.

This ledger records research and review readiness only. The 23 bundled adaptations (11 from 2026-09-29, `code-reviewer`'s, and 11 from 2026-10-02) were each adopted after the person's explicit request; future additions still require checking the candidate against the current persona manual, project rules, actual task, required tools, and measured results. An available skill is not evidence that a Session used it: use requires a receipt tied to that Session and skill.

**How the skills reach a role.** A launch prompt lists each enabled skill with its name, purpose and its own quoted "Use this skill ..." sentence, and asks the role to compare the task with them before starting. Before this change the prompt repeated the skill's ID where its description belonged; on the maintainer's machine 33 of 72 role launches had carried a skill and none had recorded a skill receipt.

**2026-10-02: only the skills that can apply.** The launch prompt is read on every call of the Session, so it lists only the enabled skills that can apply to the task. A dispatched child's declared writes are compared with the kind of code a skill is about, where its own "use this skill when" names one: `golang-concurrency` (Go files) and `frontend-component-build` and `frontend-design` (web files). When every declared write is another kind of file, that skill is left out of the prompt but still written to the launch and kept in the snapshot. Unknown writes list everything. With nothing to list, the section is one line. Source and digest moved out of each entry into `snapshot.json`, and the usage paragraph was shortened and is said only above a non-empty list. The bytes before and after are in [Session personas](personas.md#carried-once-per-launch).

## Original skills

A skill written for Clawdline has no upstream file, commit or digest to pin, and inventing a URL
would make the ledger claim a review that never happened. It is recorded instead as its role's
conclusion `original_skill`, with no candidates and an `original_skill` object: the skill `name`,
the `path` of its bundled text, `written_on`, `license` (the repository's own, MIT) and `why` no
upstream text was used. In [`builtin_skills.go`](../internal/domain/squad/builtin_skills.go) its
source is `persona.Original`. The check requires the two to match in both directions: every
`persona.Original` row has a ledger entry naming the same skill, and every ledger entry has its
text at `internal/domain/squad/builtin_skills/<name>.md`. `--verify-upstream` reads nothing for it.
