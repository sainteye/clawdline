Clawdline · cross-session protocol

One session, sending work to another.

Clawdline lets an assistant session hand a piece of work to a second session running on the same machine — in its own terminal tab, with its own instructions, reporting back through a file. This page is the whole contract: the files, the routes, the guarantees, the refusals, and where each guarantee stops. Read it once and you can dispatch correctly, and say what every answer you get back is worth.

01Three parties, and the middle one is the app

A session you are talking to is a session you are waiting on.

Some of what people ask for does not need the conversation it was asked in: run the suite, draw the icon, read this diff and tell me what is wrong with it. Doing that in-line costs the one thing the conversation is for, which is your attention on the thing you were actually doing. Dispatch is the way to say do this over there and be told when it is done.

Root
A session you are in. It writes a task down and asks for it to be run. Nothing else — it never touches a terminal, and it does not learn the child's terminal id until the broker tells it.
Broker
Clawdline. It checks the ask, records it, opens a terminal tab, types the first message into it, watches for the answer, adds up what it cost, and tells the root.
Child
The session the broker opened. It does exactly one task and writes down what happened. It never learns who asked. It may hand parts of that task to children of its own; those may not.

There is a second motion on the same machinery. A dispatch sends an errand out and waits for it to come back; a handoff sends the line of work itself on and expects nothing back. Section 17 is that one.

What it costs, before anything else

Dispatching is remote code execution with a second step. It does not type a line into an existing session — it opens a new terminal tab, starts an assistant in it, and gives that assistant instructions written by somebody else. Anything that can dispatch can run programs on the machine, as you, in a directory it chose, for up to four hours. Everything in section 18 follows from that one sentence.

02The filesystem is the protocol

Everything a child needs and everything it produces is in one directory.

That is the interface rather than an implementation detail, and it is a directory rather than a socket for a specific reason: a child is an ordinary assistant session with no special client library. It can read a file and write a file. Anything that required it to hold a connection, speak a protocol, or keep a credential alive across a context compaction would be a design that only works when the child is having a good day.

/tmp/.clawdline/                 # 0700
  <task-id>/                     # 0700 — lowercase UUID
    task.json                    # the root writes this, before dispatching
    CHILD.md                     # the app writes this, just before injection
    DISPATCHING.md               # …and this, only for a child that may hand work on
    result.json                  # the child writes this, when it is done
    artifacts/                   # whatever the child was asked to produce
    work/                        # heavyweight scratch; reclaimed with the task

0700 on both levels, and /tmp is a shared directory on a Unix machine — so a task directory is readable by you and by root and by nobody else on the box. It holds instructions and outputs, and it never holds a secret: not the orchestrator token, and not the task secret.

An isolated task's checkout is deliberately elsewhere, under the application's own support directory rather than in /tmp or inside the repository. That keeps OS cleanup from leaving stale git administration records behind, and keeps another session's git status from seeing a checkout that is not its business. The protocol directory above is unchanged by isolation.

03task.json, field by field

The file is written first; the dispatch carries only an id and a secret.

Instructions are the part most likely to be long, to contain quotes and newlines and someone's Chinese, and to be edited and re-sent. Putting them in a file that the root owns and the app validates keeps all of that out of an HTTP body, and makes a retry the same request rather than a new one.

Two fields people get wrong

root.session_id is nullable on purpose. A root that cannot work out its own id still gets to dispatch, because a best-effort field must not be a required one — otherwise the honest answer “I don't know” becomes a reason to invent something. Two things follow, and the second surprises people: the task is not told when it finishes, so the dispatcher has to poll; and its row has nothing to sit under, because a listing indents a child beneath the session that asked for it. A task that named nobody is filed under nobody, and floats wherever the sort puts it.

The broker does not trust the declared id on its own. At dispatch it accepts either the watched terminal id or the current conversation id and resolves it among the live sessions of the declared assistant. When exactly one of them matches, that session's process-bound conversation id becomes the single key used by completion notification, grouping, capacity and the root-close cascade. When none matches, or the answer is ambiguous, the id you supplied is stored exactly as you wrote it and the dispatch still succeeds — what you lose is those four things, not the task. A stale rollout, a leftover hook on a reused tty, or a tab now occupied by the other assistant produces root_unresolved in warnings rather than a silent orphan — it never mounts a child under the wrong row.

plan is the graph, not this task's job. The same text goes in every task of one dispatch, and it sits near the top of the briefing, above even the language rule, because it is the context every other line is read in. A child that knows its answer is one of four being joined together writes something joinable. Leaves get it too, and that is the half that matters: a leaf that knows what its output feeds is the difference between an answer and an essay.

Writing the file

Write task.json with an editor or a heredoc rather than assembling it in a shell string. Some assistant harnesses screen commands by shape and refuse a JSON-building one-liner — a brace beside a quote reads as obfuscation — and that refusal is a prompt with no “always allow” on a tab nobody is watching.

Sending it

TASK=$(uuidgen | tr 'A-Z' 'a-z'); SECRET=$(openssl rand -hex 32)
umask 077; mkdir -p /tmp/.clawdline/$TASK/artifacts   # …and write task.json into it

curl -s -X POST http://127.0.0.1:7717/v1/orchestrator/tasks \
  -H "X-Clawdline-Orchestrator: $(cat ~/.config/clawdline/orchestrator-token)" \
  -H 'Content-Type: application/json' \
  -d "{\"task_id\":\"$TASK\",\"secret\":\"$SECRET\"}"

The body is two fields and neither of them is the work. There is no Idempotency-Key, because idempotency is already carried by task_id: send the same one twice and the second call answers 200 with the existing record, having opened nothing. A 200 means registered and being opened, not running.

04The gates a dispatch passes, in order

Each one has its own typed code. Branch on the code, never on the status.

  1. The credential, and the switch. A missing or wrong X-Clawdline-Orchestrator header is 403 forbidden, and so is a machine where the orchestrator is switched off. It is 403 rather than 401 deliberately: 401 is this server's answer to no paired device, and pairing a device would not help here.
  2. The file. Missing, unparseable, or a field out of range is 422 bad_task, with the offending field named in message. Fix the file and re-send the same id.
  3. Capacity. A dispatcher's own slots being full is 429 over_capacity with retry_after in seconds. Registered-but-queued tasks count toward this from the moment they are registered, so an unbounded queue cannot bypass the limit.
  4. Depth. Past the floor it is 409 depth_exceeded, and that is not a retry — the work is yours to do.
  5. The assistant's own quota. An account reading exhausted is 409 assistant_exhausted, carrying alternatives: every other assistant's availability and detail, so the refusal itself says who to send the work to instead.
  6. Isolation feasibility. A repository with no commit to base a worktree on, or a volume with less than 2 GB free, is 409 worktree_unavailable — an environment refusal rather than malformed JSON.
  7. Claims. A live task from another definitely identified root holding an equal, ancestor or descendant path is 409 workspace_busy, before serialization, before any tab, before the advisory directory warnings. The rejected task is not registered.
  8. The brake. More than ten dispatches in ten minutes — or one full tree's worth, if that is larger — is 429 rate_limited. Handoffs share the same brake, because a loop that opens tabs is the same loop whichever route it calls.

Two of these are cheap on purpose and answer early. Quota is one read of small local files, cached for a few seconds, so it answers before any git subprocess is started. Claims are compared under the same lock that registers the task, so there is no window in which two roots both pass.

Depth stops at two, and the floor is what has teeth

Dispatch without a floor is a fork bomb with a language model in it. One task becomes five becomes twenty-five, each a real terminal tab running a real assistant against a real bill, and the failure mode is not “it got slow” — it is a machine with sixty tabs open and no obvious way to tell which of them started it.

So the tree has a bottom, and it is close to the top. A root's children may dispatch. Their children may not. Five and three is twenty tabs at full stretch, which is already more than anybody wants to audit; five, three and three would be sixty-five.

The floor is enforced twice, and the two fail differently. The briefing says so — a child with room under it gets the whole recipe for dispatching, and one standing on the floor is told plainly not to. The app refuses — a dispatch names who is asking, and past the floor it is 409 depth_exceeded. That second stop holds when the first does not, because it does not depend on the child's cooperation. A caller can lie about its identity, but it cannot lie its way up: the two names it supplies are combined by taking the deeper answer, and claiming somebody else's identity moves the task into that session's bucket rather than out of everybody's.

How far a child may go before it stops and asks

The permission ceiling defaults to full, and that default is a position rather than a convenience. On a tab somebody is watching, “ask about everything” is the careful setting. On a child's tab nobody is watching, and a session that stops for approval does not stop for a moment — it stops until the task times out, which reads afterwards as work that silently did not happen.

The narrower settings were tried and each one stops the child somewhere: ask stops on the first thing it does, which is reading its own briefing; edits gets it past writing a result but not past the ordinary shell work that handing work on consists of. Note also that a mode named for automatic behaviour is not necessarily the same mode on every model of the same assistant — which is disqualifying for a field a task fills in, since a word here has to mean the same thing to every session a task can name. The three values are ask, edits and full, and each was read back off a real status line on more than one model.

What the setting does not widen is who may dispatch. That is still a file only a local process can read, and a child already has a shell — the setting changes how many buttons a person has to press for work they already authorised, not what that work can reach. Two doors also sit in front of the session rather than inside it, and no permission value reaches either: a fresh directory's trust prompt (which Clawdline answers once per task, with an audit receipt), and the assistant's own command screening.

05The lifecycle

Eight states, four of them terminal, and one that is terminal without ever having started.

queued
Registered: the file validated, the secret's hash stored, the caps checked. A task without serialize is here only until a tab is asked for. A serialized task stays here until every operation it named is free, and waiting_on says which older tasks stand ahead of it. Waiting does not consume timeout_minutes.
spawning
Mutexes acquired, a tab opening. For an isolated task this is when the private checkout is created — queued tasks hold no idle checkout. Failure here is spawn_failed, and the next attempt needs a fresh task id — which the respawn route mints for you.
briefed
The child's own record shows the first message as a turn it received. This is the fiddly part, and it is worth knowing what the app waits for.
success · failure
From result.json, or from the completion route, whichever arrives. Both go through the same finalize.
timeout
briefedAt + timeout_minutes. There is a second way to get here that is not a clock: if the child's terminal disappears from the session list for more than a minute while the task is briefed, the task is failure with child session ended without reporting. A closed tab is a finished task in every sense except the one that would have been written down.
cancelled
Somebody asked — through the cancel route, or by closing the root session.
spawn_failed
The tab never happened, or never got briefed inside four minutes, or was typed into five times without the child ever recording the message, or the app restarted while the task was spawning.

A spawn_failed task is retried by the broker, not rewritten by the root. It was 34 of 206 dispatches on the machine this was measured on — 33 of them Codex — and the old answer was that the root writes the whole task.json out again under a fresh id, because that id is finished and re-sending it just returns the terminal record. POST /v1/orchestrator/tasks/:id/respawn copies the original file with a fresh task_id, mints a fresh secret unless the caller supplies one, and dispatches it through the ordinary gate with every capacity, depth, claims, quota and serialization rule applied again. instructions is why it copies the file rather than the record: the registry never held it.

Only spawn_failed may be retried, because it is the one terminal state meaning nothing ran; anything else is 409 not_respawnable. At most two respawns descend from one original, counted over the whole family below it rather than along any one chain — so a retry of a retry cannot launder the cap by being the first from its own immediate parent, and neither can asking the original a third time, which is the shape a caller actually falls into because the id it has in hand is the one that failed — and the third is 409 respawn_exhausted. Each new task records respawn_of and respawn_generation, so a chain reads as a chain in the registry instead of as three unrelated tasks with the same title.

Why briefing takes as long as it does

It waits for somewhere to type. A tab in the session list is not that, and neither is a process with the right name: an assistant still starting its tooling has a readable banner and no composer, and a briefing typed into that is swallowed without anything reporting a failure. So the app waits until it can see the assistant's own empty composer.

Then it waits for evidence the sentence arrived. Typing into a terminal proves that bytes reached a tty and nothing more, so the task stays in spawning and keeps its secret until the assistant's own record carries that task's first user turn. Only that moves it to briefed. If the record still has no such turn once the receipt window has passed and the empty composer is back, the app types it again — up to five attempts, then spawn_failed. It will not send a second copy on the strength of a missing file alone: both assistants write the user turn before they begin it, so a message that was accepted closes the gate before it can be run twice.

Cancelling, and what a closing root takes with it

Closing a root session cancels every live task that session dispatched and closes each child's tab first, before the root's own. The order is not cosmetic: a task is matched to its root through the tab that is about to disappear, so a root closed first is a root that can no longer be matched to anything, and its children run on reporting into a conversation that ended.

The cascade reaches both levels, deepest first, and it is gathered from the finished children too — a child that reported while the work it handed on is still running would otherwise leave a grandchild belonging to nobody. Cancelling a single task does the same thing on a smaller scale.

Only an explicit close cascades. Closing a tab by hand does not, and the app never watches a root for signs of death: “not in this reading” is a sentence that is also true of a terminal that lost its accessibility permission for a moment, and the cost of being wrong there is somebody's work killed mid-turn.

Restarts

A briefed task survives a restart. Its secret is on disk as a hash, its result is on disk as a file, and its timeout is arithmetic on a stored timestamp — so the app comes back up, reads the registry, and carries on watching. That is the one restart case that matters, because it is the one where a child is out there doing work. A task caught in spawning is failed closed instead: once a task starts opening, the recoverable queued secret is gone, and failing closed beats risking a global operation running twice.

06The briefing, and the first line

One line into the terminal; everything that would not fit is in a file beside it.

You are a Clawdline CHILD agent for task 3f9a21bc-… . Read
/tmp/.clawdline/3f9a21bc-…/CHILD.md and follow it exactly. TASK_SECRET=…

One line, because it is typed into a terminal and Return ends it. CHILD.md — written by the app immediately before injection — carries the rest: where the task is, where the outputs go, how long it has, the graph it is one node of, whether it may dispatch and how many, that it must not read other task directories, and exactly what result.json has to look like.

How to dispatch is not in there. It is in DISPATCHING.md, written beside it and only when the allowance is above zero, with the machine's house rules appended; CHILD.md keeps one line naming that file. Measured across 206 dispatches on one machine, 28,323 characters of instructions on how to dispatch went into every direct child's briefing and not one of those 206 ever dispatched anything. The pointer is worth following rather than merely polite: the credential path, the root.parent_task rule and the curl appear only in DISPATCHING.md, so the briefing no longer hands the credential over and a child that skips the file has to go and find one. A strong pointer, not a lock — the clawdline skill carries the same recipe — but a convenience summary back in CHILD.md would undo even that.

It also says what language to speak. The briefing itself is English so that every assistant reads it the same way, but the person watching the tab reads whatever Clawdline is set to — so the file names that language and asks for the summary in it. The one fixed line the child says before anything else rides in the typed message, ahead of “read CHILD.md”: an assistant answers the line before it opens the file, and the first thing on the screen should be what the tab was sent to do. A tab that opens and starts working in silence is a tab nobody can tell apart from a stray one.

Where the secret lives

The secret is in the message and not in the task directory, and that asymmetry is the whole design. CHILD.md sits in a directory; the message goes into a terminal's input. A file there is a thing that can be read later, by something else, after the task is over. The plaintext secret stays in the app's memory until the child's own transcript proves the line landed, and then it is gone.

Saying something mid-task

Two narrow channels exist so that a child does not have to stay silent until it is finished.

A progress note — POST /v1/orchestrator/tasks/:id/progress, authenticated by the task secret — is one sentence of at most 300 characters. The title was fixed at dispatch, and by the time a result exists somebody else may have spent an hour on the same thing; this is the seam between those two moments. The newest five are kept and appear on the task record and on every outstanding-work row. Repeating the newest sentence is accepted and ignored, because a loop is not news. A terminal task is refused with 409 not_live.

The briefing asks for the first one inside three minutes, before the work rather than during it: one sentence saying what the child has decided to do now that it has read the briefing and task.json. That is the only thing that lets a wrong direction be cancelled at minute three instead of minute twenty-six — the two dearest cancelled tasks measured on one machine burned 18.5M and 16.5M tokens before anybody could tell what they had set off to do. Every later note is the ordinary one: sent when what the session is doing stops matching the title it was given.

An agent notification — POST /v1/orchestrator/tasks/:id/notify — pushes content rather than state: today's forecast, the URL somebody was waiting for, the one answer whose value is arriving on time. It is scarce by construction: 80 title characters, 500 body characters, five per task, thirty per machine in a sliding hour, and valid only while the task is live or for 60 seconds after it finished. A local root or script can send the same kind of thing with the machine token at POST /v1/orchestrator/notify. If the person has turned agent notifications off, both routes answer 409 agent_notify_disabled without attempting delivery or spending an allowance — and the right response to that is not a retry. Leave the content in result.json, and say honestly that the notification was refused.

07result.json is the signal

Written last. The moment it exists, the task is considered finished.

{
  "clawdline_protocol": 1,
  "task_id": "3f9a21bc-8d4e-4c1a-9f2b-6a7e5d0c1234",
  "task_secret": "…the value from the first message…",
  "status": "success",
  "summary": "Wrote a 1024×1024 SVG portrait; border and lettering hand-pathed, no raster.",
  "symbols": ["Orchestrator.Landing", "updateLanding(taskID:secret:raw:now:)"],
  "artifacts": ["artifacts/portrait.svg"],
  "verification": {"runs": 2, "seconds": 940, "last": "pass", "scope": "unit suite + web checks"},
  "finished_at": "2026-01-14T10:41:55Z"
}

Written atomically — to a temporary name and then moved — so the watcher never sees half of it. The app checks once a beat for every briefed task, hashes the supplied secret and compares it against what it stored at dispatch, in constant time. A file whose secret does not match is ignored and logged once: a wrong secret in a task directory is either a bug or somebody poking, and neither is a reason to finalize somebody's task.

status
success or failure. Use failure when the work could not be done; a summary that reads like success is worth less than an honest failure.
summary
One paragraph: what was done, or why it could not be.
symbols
Every identifier the change introduced — new functions and types, new fields, new string keys, the names of test groups added. Names, not descriptions; [] says positively that there were none, where an absent field only says the child did not answer.
artifacts
Paths, relative to the task directory, of what was produced.
verification
Optional. What proving the work actually cost — section 8.

Why symbols exists. A shared working tree makes authorship unreadable from the diff alone: by the time a root comes to commit, the files a child edited may hold two or three sessions' unfinished work, and vocabulary is the only reliable way to tell one session's hunks from another's. Guessing that vocabulary has produced staged trees that would not compile, because a hunk that read like one session's work actually called another session's new function. The child's briefing asks for the list; the broker does not read it — the record keeps status, summary, artifacts and the optional verification object, and ignores every other key. symbols is written for whichever root opens the file, and a root has to open the file to get it.

There is an HTTP way to say the same thing — POST /v1/orchestrator/tasks/:id/complete — and it is optional on purpose. The file is the protocol and the route is a convenience. A child in a sandbox with no outbound network finishes correctly. A repeat is 409 already_done rather than a silent overwrite: the first report wins, and the second is told so rather than quietly replacing a summary somebody has already read.

What it cost

Every finalized task carries a usage object, and it is best-effort by construction: harvesting it never blocks a finalize and never fails one. A task that finished is finished whether or not the accounting worked. The numbers come from the ordinary transcript the child left behind, not from anywhere new. A dollar figure is computed only for models with a published per-token price, and is null otherwise — including for plan-billed assistants, where a currency figure would be a made-up number wearing a currency symbol. Tokens are still counted, and that is the honest reading rather than a gap.

08Verification is budgeted

One relevant proof, reported as a number rather than an impression.

A child that keeps re-running a full suite is paying a project's largest fixed cost over and over. The protocol's answer is a budget with a receipt on the end of it.

  • Do run one verification that actually proves the change: compile, the tests covering what was touched, and one red-before-green run for each test added. A test born green proves nothing — break the thing once, watch the test catch it, then fix it. Iterating until something first compiles and passes is ordinary work and is not what the budget is about.
  • The budget is one third of timeout_minutes, or three full-suite runs, whichever comes first. On reaching it the child stops verifying and says in its result what state the work was in, rather than spending the rest of its time trying to reach green.
  • Do not re-run a full suite after every small edit, run a suite unrelated to the paths claimed, repeat a green run to see whether it was flaky, or treat restarting the application and looking at it as acceptance.

The receipt is an optional object in result.json:

"verification": {"runs": 2, "seconds": 940, "last": "pass", "scope": "unit suite + web checks"}

runs and seconds are non-negative integers, last is pass, fail or skipped, and scope is a short free-text description. A well-formed object is stored on the task record and can be read back over the API. Older results without it work unchanged, and a malformed object is ignored rather than turning an otherwise authenticated success into a failure — verification metadata never changes the authenticated outcome. Without a number, “it kept re-verifying” is an impression rather than a finding.

A green tree is not evidence about HEAD

In a shared checkout, a passing suite is the union of everybody's work, while a commit is only the committing session's slice. So a suite passing in the tree says nothing about whether the branch still compiles after a partial commit. Before taking one, ask what else defines what you are taking: a declaration without its values, a call without its function, a case without its enum. Each of those passes in the tree and fails on the branch.

09Claims: reserving what you will write

A dispatch-time reservation, compared by path, arbitrated between roots.

Each entry in claims is relative to project_dir. At registration the broker resolves that directory once, normalises the relative claim, and freezes the joined absolute string in the lease. It never resolves the possibly nonexistent target, so creating the file cannot change its key. Comparison is exact and case-sensitive, by path component: equal paths conflict, and so do ancestors and descendants — Sources covers Sources/Orchestrator.swift, while a/b and a/bc are unrelated.

claimsMeansBehaviour
one or more pathsthe task declares exactly these write scopesreserves their frozen keys; two disjoint declarations can silence the directory-level warning
[]the task positively declares that it is read-onlyreserves no lease, never conflicts, never receives 409 workspace_busy, and still participates in that silence
absentthe write set is unknownreserves no lease, keeps the directory-level warning about every pair sharing a project_dir, and the dispatch reply carries a claims_missing warning

An empty array gives read-only work an active, harmless declaration. Silence therefore has exactly one meaning: both tasks supplied enough scope information to prove their claim sets do not intersect. Merely omitting the field never makes that assertion.

An absent field is answered out loud, and only an absent one. 60.7% of the dispatches measured on one machine declared nothing at all. Declaring costs the root about twenty output tokens; a collision costs a whole task, which on that record is three to eighteen million — so the dispatch reply carries warnings:[{"code":"claims_missing",…}], on the first request and on the idempotent retry alike. It is never a refusal: a root that has not worked its write set out yet must still be able to dispatch. "claims": [] does not warn, and that difference is the point — warning about a positive read-only declaration would teach callers that the field is noise, which is how omission reached 60.7% in the first place. The best evidence for the warning is not an argument: the root session that specified it dispatched the review of its own delivery without claims, and drew the workspace_overlap notice that claims_missing exists to prevent — on the day it implemented the guard.

There are two ways to get this wrong, and only one of them is loud

Omitting claims is the quiet one, and it reads as caution while behaving as noise: with no declaration the broker cannot prove two tasks are disjoint, so it falls back to warning about every pair that shares a directory — a stream of notices, none of which describes a real conflict, while the one genuine collision is caught by the mechanism that needed the field. Claiming too widely is the same error pointing the other way, and it does announce itself: an over-wide claim blocks other trees whether or not the task touches it, and the exit audit names every claimed path the task never touched.

Arbitration, and what the refusal tells you

A live claim from a different root refuses the new dispatch immediately with 409 workspace_busy — before serialization, before warnings, before any tab. The error names the blocking task, its title and root label, when it was created, every conflicting absolute path, and an advisory retry_after. It also carries two fields that make it self-sufficient, so nobody has to follow up with another request:

  • age_seconds — how old the blocking task is, computed against the answering request's own clock.
  • root_key — a short stable hash of the blocking task's root tree. root_label is self-reported prose and can be stale, or shared by two unrelated trees that both call themselves the same thing; root_key is the same tree's identity every time.

Tasks in the same root tree may overlap, because that root owns the graph and may have ordered the work itself; their dispatch succeeds with a claims_overlap warning naming the other task and the conflicting paths. If either side's root cannot be resolved, dispatch also succeeds, with the same warning shape under claims_overlap_unknown_root — an unknown root never has the authority to hard-block somebody else. A refused dispatch does not spend a ticket in the ten-minute brake, so following the retry advice cannot turn repeated workspace_busy answers into rate_limited by itself.

Giving paths back early

Terminal state is not the only way a lease ends. A task that has finished editing some or all of what it declared can hand those paths back with POST /v1/orchestrator/tasks/:id/claims/release while it is still briefed or spawning, and a dispatch blocked on exactly those paths can retry immediately. This is the only way to break a circular wait where two roots each hold a path the other one needs: the retry advice on a 409 says “wait”, and nothing releases on its own until a side chooses to.

Release is compared the way arbitration compares claims — ancestor and descendant, not string equality — so naming a path inside a directory-shaped claim frees that whole claim key, because a directory claim is one atomic reservation rather than a set of the files under it. It is idempotent: a path already released, or never declared, is silently a no-op. It is refused for an unknown task (404 not_found), a terminal one (409 already_done — its claims are already released in full), a still-queued one (409 not_started — cancel it instead), or a malformed path (400 bad_request).

Release is a machine-level permission, like cancel. The request carries only the machine token, which does not identify which root is calling, so any root holding it may release any task's claims — including one that is currently blocking it. The audit line names the task and the paths freed, because there is no caller identity to record.

The exit audit

Purely observational, and never a gate: when a task reaches a terminal state, the broker checks each declared claim against the filesystem and reports which ones were never modified after the tab opened. A directory-shaped claim is judged recursively rather than by its own timestamp; the walk skips version-control and dependency directories and stops after a bounded number of entries, and a claim whose subtree is larger than that is left out of the audit entirely rather than judged from a partial walk.

Untouched paths land on the task record and in one line appended to the root's completion notice, with a reminder to claim narrower next time. Only success and failure are judged. A task that never spawned has no baseline; and timeout, spawn_failed and cancelled leave the ending ambiguous — saying both “it may still be writing” and “it never touched this” about the same task on the same line was the bug this exclusion exists to prevent.

An honest boundary

Claims are a dispatch gate, not filesystem enforcement. The broker does not stop a child from writing outside what it declared, and does not infer a write set from instructions. What dispatch-time refusal buys is the removal of the negotiation window in which two already-briefed tasks keep editing while their roots work out what to do. Cleanup work is work too: a separately dispatched cancel, revert, rollback or removal task declares every path it may change exactly as entering work does.

10Serializing a machine-global operation

For scarce operations rather than directories.

Two tasks that both run the build can name "serialize": ["build"] when the build writes a fixed output path. Without that mutex, two otherwise unrelated roots overwrite the same file — a fixed temporary binary path is the usual real example. The namespace is machine-global and deliberately ignores roots.

  • A task acquires all of its names together as it leaves queued, and holds them until any terminal state. If any one is held, it stays queued.
  • Waiters sharing a name are FIFO by creation time, including waiters from another root. A multi-name request never holds a subset, so crossed acquisition orders cannot deadlock.
  • A queued response and every record include waiting_on when blockers exist — it can name a current holder or an older queued waiter entitled to the name first.
  • Cancelling a queued task is immediate, opens no tab, and pumps the next eligible waiter. Every other terminal outcome pumps the same queue, and so does startup.
  • A queued task already occupies its dispatcher's slot and the machine-wide slot: counting registration rather than open tabs is what stops an unbounded queue from bypassing the caps.

Do not reach for worktree isolation to evade a serialize token. Isolation changes the checkout; it does not create a second machine.

11Isolation: a branch, not a diff

A clean private checkout, and a delivery that survives the session that made it.

"isolation": "worktree" asks for a clean independent checkout and a delivery branch named after the task. The broker resolves the requested base to a commit and records that immutable value, because branch names and HEAD move while other sessions commit — the resolved commit is the receipt for what the child actually started from. A dirty base is admitted with a warning: uncommitted files do not cross into the clean checkout.

The child commits early, only on that branch, and never pushes or switches branches. At finalize the broker reads git itself and records the branch, the base, the head, a commit count and whether the checkout was dirty; those last three are best-effort and may be null.

git -C <project_dir> log --oneline <base>..clawdline/task/<id>
git -C <project_dir> diff <base>...clawdline/task/<id>
git -C <project_dir> merge --no-ff clawdline/task/<id>   # or cherry-pick
git -C <project_dir> branch -d clawdline/task/<id>       # only after landing

Relative claims under project_dir are discarded with a warning for an isolated task, because the child edits the separate checkout and not those shared-tree paths. Machine-global resources still belong in serialize. This also removes a timing mismatch that shared-tree work has: a claim is released at terminal state, but an isolated delivery is not landed until a root integrates it — the delivery stays on its branch until then. That safety property has a corollary worth stating plainly: a terminal child state cannot be the completion state of a code-producing graph. The delivery is durable, and still pending.

A slice big enough to be worth dispatching is big enough to lose — the timeout is bounded, an assistant can exhaust its quota mid-task, and a context window can fill. A long or multi-file slice therefore goes out isolated, commits each milestone on its branch rather than at the end, and says through a progress note when the work stops matching its title. A death in the third hour then costs one hour. Conflicts are the visible cost of parallel work and are resolved at integration; review the branch before landing it, because a commit has not become trusted merely by being isolated.

12Landing is a root obligation

The lifecycle answers whether a child ran and reported. It deliberately does not claim the code arrived anywhere.

success supplies delivered. An independent review verdict supplies reviewed and opens pending landing. Neither is landed. The root that dispatched the graph owns the pending landing unless a named root accepts it through a handoff; an unspecified future session is not an owner. The graph's plan therefore names the delivery branch, the target branch, the landing owner, the review node and the root-owned closure before the first child is dispatched.

Recording it

POST /v1/orchestrator/tasks/:id/landing takes state plus optional target, delivery, commit and note. pending and abandoned accept either that task's secret or the machine token; landed accepts only the machine token. Repeating pending preserves the original since while filling in anything newly known.

Before writing landed, the broker resolves the supplied commit as a commit object inside the task's own repository, resolves the local target branch, and proves the former is an ancestor of or equal to the latter. Caller-supplied revision expressions are replaced by canonical object ids in the receipt, and the moment of proof is recorded separately from the moment the obligation began. Arbitrary text, a remote-only ref, or an unrelated commit is refused with 409 unverified_landing; a pending edit racing the git checks is refused with 409 stale_write. Both landed and abandoned require a terminal task and are final — genuinely reopened work gets a new task, and abandoned is an explicit decision not to land the delivery rather than a pause.

GET /v1/orchestrator/landings lists every current pending obligation with its title, owner root, original claims, target, note and age. Pending obligations are exempt from the registry's ordinary record cap, so age alone cannot erase an unresolved row. When a task with claims reaches a terminal state with no landing record at all, its completion line reminds the root to record one — suppressed when every claim was judged untouched.

A signpost, not a gate

Landing state does not retain claims, extend their lifetime, refuse a dispatch, freeze a file or stop a commit. It makes an unfinished obligation queryable, so another root can decide whether to wait. Claims arbitration and ordinary pre-commit discipline remain the separate mechanisms that actually prevent collisions.

Closing it

After review, the root checks the receipt and the verdict, reads the target repository's current head and status, integrates without absorbing another session's uncommitted files, tests the exact integrated tree, and records the resulting target commit. Only then may it report the code change complete. An overlapping dirty tree is a landing delay, not a completed outcome: the obligation stays pending while the root coordinates with the owning session and retries when integration is safe.

If the root must stop first, its handoff package names the delivery branch, base and head, the target branch and its current head, the verdict and test receipts, the overlapping paths and known owner, and exactly one next landing action. The original root remains responsible until the handoff receipt confirms that the first line reached the named receiving root — and even then the receipt transfers ownership, not completion.

13What is still outstanding

Including the work a private checkout hides.

A finished delivery sitting on its own branch appears in no git status, no git diff and no file listing of the shared checkout, and its claims were released the moment the task ended. A session that asks “has anybody done this?”, looks at the tree, sees nothing and does it again has been burned by exactly that. GET /v1/orchestrator/inflight?project=<dir> is the answer to that question — and GET /v1/orchestrator/tasks/:id/inflight is the same list for a child, which reads the repository off its own task and authenticates with its own secret, because a child has no machine token and should not be taught to read one. The asking task is left out of its own answer.

visibilityMeans

A row leaves the list because git says so, not because somebody remembered to clear a flag: a delivery disappears when its branch is merged into the repository's head or deleted, which is the same moment the work stops being invisible. Two declared answers are honoured first, because a root saying so is better evidence than a branch this side has to guess about — landed and abandoned settle a row, and pending keeps one visible even with no branch behind it.

A task whose session died is finalized as a failure by the ordinary rule, its branch is kept because it carries commits, and it appears here as failed and unmerged — which is exactly right: the work is there, on a branch, and nobody is doing it.

14Attached follow-up tasks

A complete task, delivered into a session that is already open.

Some sessions are worth keeping alive between jobs — one that takes small batches, one that reviews each finished feature. The problem with feeding such a session by hand is that work typed into an existing session carries no task record: it holds no claims, signals no completion, appears in no outstanding-work answer and is counted in no usage. A standing session fed that way is invisible to every safety mechanism on this page, which is worse than a session that costs a tab.

attach_session closes that gap. The task still has a fresh id and secret, its own directory and briefing, its own claims, serialize tokens, timeout, usage, result signal, landing record and outstanding-work visibility. The only difference is that the ordinary first line is typed into the named existing session instead of into a new tab. The public record carries an attached flag and the session it went to.

  • The id is resolved against the same terminal-neutral session list a caller reads with the machine credential. A plain shell has no assistant to read a briefing; the resident assistant must match the task's assistant.
  • One session runs at most one live Clawdline task. The single-flight check is repeated under the registration lock, so two concurrent requests cannot both pass a stale inventory.
  • If the session's cached state says it is waiting and a screen reading confirms a menu is up, the dispatch is refused before anything is typed or any record is created — retrying the same body later is safe.
  • An attached task keeps the standing session's existing depth, including at the depth floor — a session Clawdline did not open for a task is refused with attach_not_managed long before depth is considered. It opens no tab, so it spends no child, grandchild or machine tab-opening capacity — but it is a live task, it passes the rate limiter and the quota gate, and it holds its ordinary claims and serialize reservations.
  • The task does not own the tab. Success, failure, timeout, cancellation, a root-close cascade and any tab-linger setting all leave the standing session open. Its briefing says that writing result.json completes the task and does not end the session, which can then take a later follow-up assignment.

Seven typed refusals belong to this path alone: 404 attach_session_not_found, 409 attach_unsupported, 409 attach_not_managed, 409 attach_assistant_mismatch, 409 attach_session_occupied, 409 attach_session_busy, and 502 attach_delivery_failed — that last one meaning validation and registration succeeded but the line could not be typed, leaving the task record in spawn_failed.

An attached task is not held to the four-minute clock, and the difference is worth budgeting for. That clock asks whether a tab this dispatch opened ever reached a prompt; an attached task has no tab-opening phase at all, because its first line was typed before registration returned. Waiting longer while the standing session's owner answers a menu therefore does not relabel delivered work as spawn_failed. The wait is still bounded — the task's ordinary timeout_minutes runs from that delivery, and expiry finalizes it as timeout, releases its claims and serialize tokens, and returns the session to its earlier role. But notice what that means end to end: an attached task's total wall-clock budget can reach twice timeout_minutes, once waiting to be picked up and once running.

The rule this exists to make keepable

With no follow-up task carrying claims, a standing session must not write to the shared tree at all. A review session satisfies that by construction, because a reviewer produces findings and not bytes. An odd-jobs session does not — which is the whole reason this mechanism has to exist before one is kept alive.

15Scratch space, and when it is reclaimed

Heavy temporary output has a shorter life than the task directory around it.

Repository snapshots, build products, mutation checkouts and compiler indexes go in the task's own work/ directory rather than in a scratchpad somewhere else, so that large temporary files live inside storage Clawdline already owns and can account for. That has a matching promise on the other end:

  • work/ is reclaimed as part of finalizing the task — immediately on success, and after a grace period for every other terminal state.
  • The grace period is a setting: 60 minutes by default, 0 to reclaim immediately whatever the outcome, and -1 to leave the directory to the ordinary sweep. The default exists because a task that failed is the one whose leftovers somebody may still want to read.
  • artifacts/, task.json, CHILD.md, DISPATCHING.md and result.json are untouched by this and live until the whole task directory is swept.
  • Reclaiming a work/ that is not there counts as success, and a filesystem refusal never delays or reverses the terminal state of the task. Accounting is not allowed to hold up a finalize.

The consequence for a child is one line long: copy anything worth keeping into artifacts/ before writing result.json. A diagnostic log or a diff left in work/ is a file you have asked to have deleted.

Clawdline also keeps an append-only ledger of the scratch directories it can prove belong to a child, recorded only after that child's own first turn proves the marker. The safety boundary is what the ledger can name: the app does not enumerate a temporary directory and then apply rules to whatever it finds there. Interactive sessions, directories with no receipt and other tools' files are outside the candidate set altogether, and a read-only inventory route reports each owned path with a decision of held, releasable or unknown — where unknown is held, always.

16Waiting for somebody else's files

A relationship the broker remembers, not one that lives inside one assistant.

When a root needs paths another session is still editing, it must not create a relationship that exists only inside one vendor's messaging. It resolves both parties through Clawdline's own session and git readings and registers the wait with POST /v1/orchestrator/waits, naming the repository, the exact paths, the owner and waiter session ids, the reason and the release condition. The broker canonicalises the paths, deduplicates the same waiter, persists the group, and delivers a typed request into the owner's terminal.

  • Both ids are terminal-neutral session ids, read from the session listing that the machine credential can open. Registering a waiter the machine cannot find is 404 waiter_not_found.
  • If the owner is genuinely showing a menu, the route answers 409 owner_busy and nothing is sent — retrying the same registration is safe. A session that is merely working, or invisible to this machine, continues to delivery, so an absent owner becomes 502 request_delivery_failed: a send was attempted and did not arrive, rather than being misreported as busy.
  • The registry row is written before delivery, so a retry re-attempts only the missing deliveries.
  • Release is always explicit. The recorded owner calls the release route after committing or otherwise releasing the paths, and every waiter is sent a notice naming the repository, the paths, the commit if there is one, and the requirement to re-check the branch head, status and diff. Partial delivery is recorded, so a retry does not notify successful recipients twice. 403 wrong_owner protects the relationship; a waiter abandoning its work removes only itself, and 403 not_waiter protects everybody else's.
  • The broker never infers release from a transient clean status, and an owner session disappearing does not remove a wait.

The relationship shows up on session rows as a quiet overlay — the blocked session names who it is waiting on, the owner names who is waiting on it — without changing the session's own state. That distinction matters: a session marked as waiting for a person is the loud one that earns attention and a push notification. A peer wait is drawn quietly, so that an idle-looking but parked session is safe for somebody to leave open.

Two namespaces, and only one of them is listed

A root identifies itself in task.json with whatever id its own assistant gave it. That is not the terminal-neutral session id the app assigns and lists. Comparing one against the other is comparing two different namespaces, and a miss proves nothing.

Querying for a session by an id and getting nothing back is never proof that session is gone — it may only mean the app could not prove that id at that moment. To judge whether a root is still around, use what a listing can always promise: the working directory, label and state of a session sitting where the root said it would be, or send it a message and read whether anything answers.

17Handoff: the other motion

A dispatch sends an errand out. A handoff sends the line of work itself on.

A conversation ends before its work does — the context window fills, the phase changes from planning to building, the day ends, or the next hour would be better done in the other assistant. What usually happens next is that somebody re-describes half of it from memory to a session that starts knowing nothing, and the half nobody remembered to say is the half that mattered. A handoff is the other move: the session that has the state writes it down, and a new session picks the line of work up from that document. The file is the protocol; the app is the postman.

Closing the session that handed over does not touch the session that took over — the cascade follows parent and root links, a handoff creates neither, and that is correct: you handed the work on precisely so that it would outlive this conversation. And the sender does not have to die: a handoff is a copy of state, not a transfer of ownership. Fork a line off to run in parallel and there are simply two equal roots in one working tree, with everything this page says about claims applying to both.

There is one deliberate ownership convention on top of that transport fact. A root that must stop while holding a named pending obligation writes that obligation and the receiving root's ownership explicitly into the document, supplies the sending session's name, and waits for the picked up receipt before stopping. The receipt proves that the first line reached the named root — not that the package was understood, and not that the work is done.

When it is worth doing

Hand over when the work has to move; compact when it merely has to continue where it is. Worth a handoff: a phase boundary, a context window that is about to make the decision for you, a parallel fork, multi-day work, a different assistant or model or allowance, a different machine. Not worth one: the same harness in the same directory on an ordinary transition, work smaller than the document that would describe it, or a question you could answer in this session. A handoff is for a line of work, not a step.

The package, and the document

/tmp/.clawdline/handoffs/        # 0700
  <handoff-id>/                  # 0700 — lowercase UUID
    handoff.md                   # the sender writes this. Required, non-empty
    attachments/                 # optional. Copied, not linked

Handoffs live in their own subdirectory rather than beside the task directories, and that is not tidiness: every child briefing carries the rule do not read any task directory but your own, and a task-shaped directory that is not a task would make that rule ambiguous exactly where it needs to be crisp. The package holds no credential, because there is nothing a receiving session has to prove.

Eight headings, in this order:

  1. OBJECTIVE — what this line of work is, and what the receiver's first hour looks like. The only section that may assume nothing.
  2. KEY DECISIONS — what is settled, numbered, marked plainly as do not reopen, each with a date and where it was settled. A decision that lives only in the sender's context has nothing behind the summary of it.
  3. CURRENT STATE — done, not done, in flight, and what belongs to a different line that touches this one. Name commits by hash. This is the section that goes stale, and keeping it true is the receiver's job from the moment it takes over.
  4. REFERENCES — the authoritative sources in reading order, with their content not repeated; a document that summarises its own sources will disagree with them by Thursday. Two layers: what the receiver can read (including every attachment, named one by one — the typed line points at the document and at nothing else, so this section is the only door the rest of the package has), and what it cannot read, with where to ask.
  5. CONSTRAINTS & PRINCIPLES — the red lines. Violating one means the work went the wrong way, not that it went slowly.
  6. OPEN THREADS — numbered, each a sentence, each pickup-able cold.
  7. IMMEDIATE NEXT STEP — one entrance, naming one open thread. Not a plan; a door.
  8. VERIFICATION — three to five questions whose answers are deliberately not in this document, each naming where the answer lives.

That last section is the load-bearing one. It is not a quiz for a person, it is a fidelity check built into the handover: a receiver that can answer the questions has demonstrably walked the reference chain, and one that cannot has found a break at the cheapest possible moment to find it.

Transport is not storage

A package is swept a day after it was created, on the same clock a finished task directory is. So the package is transport — good for the hours between one session and the next — and anything the line of work will still need next week has to be durable before it is cited. References are not duplicated, but a volatile source is the exception: archive it durably first, then cite the durable copy. In the package, put the pointer, not the copy.

The route, and what the receiving session owes

POST /v1/orchestrator/handoffs takes the handoff id, the project directory, and optionally an assistant, a model, a title and the name of the sending session. The tab is made before the call answers; the typing happens after. Opening a tab is synchronous, so a machine that cannot provide one refuses with an HTTP status — but waiting for a composer, typing the line and confirming it landed run for up to four minutes after the connection has closed, so none of that can ever be an HTTP code. It is idempotent by handoff id, and the row survives a restart, so a retry after a dropped connection cannot leave two sessions holding the same line of work. To genuinely open two, make two packages.

The app opens the tab, waits, types one canonical English line naming the document path and what to do with it, confirms it landed by finding that first turn in the assistant's own record, types one receipt line back to the sender if it was told who that is, and then settles the row. It does not read the document — not to name the tab, not to summarise it, not to check its headings. An app that validated the shape of a handoff would be an app with an opinion about what a handoff is allowed to say, and the format above is a convention that ought to be able to change without a release. The row it keeps is the envelope and never the contents: did this one already go? is the one question a postman is allowed to have an answer to.

What the receiver owes is not a report to the sender — there is no channel back and none is needed. It owes the person in front of it a sequence: read the document first; walk the references and actually open them; answer the verification questions from those sources and say the answers out loud in the tab; say plainly what could not be reached, and do not fill a gap with a plausible answer, because an invented one costs more than a missing one — it stops anybody looking; continue from the open threads; and keep the current state true, because a handoff that stops being updated is a handoff that can only be made once.

There is no second route: no list, no cancel, no state to poll. The session it opened is a root, so the ordinary session surface already addresses it.

Why the boundary is a file and not an address

Once a tunnel is running, every request arrives from 127.0.0.1 — the tunnel client connects to the local port like any other program, so a request from a phone in another country has the same socket address as a curl in the next window. This feature therefore could not be built on but it came from this machine.

What separates “a local process running as you” from “somebody on the other end of a tunnel” is a file: the token is mode 0600 in your home directory, and a request either presents its contents or it does not. A page on the internet cannot read files. A phone cannot read files. A shell in your own terminal can, which is the entire point.

And that guarantee is bought by the URL rather than by a list of exceptions. Authorisation is decided before a route is chosen, on a prefix: a request under /v1/orchestrator/ is the only kind that can be answered by this token, and one not carrying it falls through to ordinary device authorisation. Hanging a tab-opening route anywhere else would mean either a paired phone reaching it, or one more special case in the ladder — and a security boundary with an exception list is a boundary somebody eventually edits.

Cancel is where the asymmetry is easiest to see. With the machine token it is the same local credential that opened the task and needs nothing else. From a paired device it is a write like any other and passes all three ordinary write gates. A device may stop work; it may not start any.

What is deliberately not a credential

A serialized task waiting in the queue has a temporary encrypted copy of its secret in the app's own store, so that the queue can resume after a restart. The key for that is a separate random file, mode 0600, created lazily and replaced only when the stored bytes do not parse. It is not derived from the orchestrator token, is not accepted by any route, and is never named or copied into a briefing, and the sealed copy is removed before the task starts opening. That is how three request credentials stay non-interchangeable without sacrificing restart recovery.

What this does not defend against

Something already running as your user can read the token exactly as it can read your SSH key. Same-uid compromise is outside this threat model. The separation above protects the narrower boundary of a child following its briefing and reading only what that briefing names — not hostile code already running with unrestricted access to the account.

19The machine coordinator, and the restart boundary

One optional role, durably bound to one process, that explains receipts and never writes them.

A machine running many sessions can register exactly one coordinator: a role that holds the machine-wide picture. It is an authenticated construction rather than a title anybody can claim. A local caller reads a terminal-neutral session id from the machine-credential session listing and posts that exact id to POST /v1/orchestrator/coordinator/register; the broker accepts only a live assistant row whose complete process-bound identity it can prove — terminal, assistant, tty, process and its current conversation. Labels, working directory, task ancestry, recency and words in a title are not evidence.

The durable record holds a stable opaque id, a fixed scope and label, and the private binding, in a mode-0600 file under an exclusive lock, written atomically and read back before success is reported. A first registration creates the id; the same identity again is idempotent; any other identity is refused with the existing coordinator's safe metadata. There is deliberately no takeover through registration, and no unconditional replace, delete or stop.

Restart continuity is identity continuity, not conversation resurrection. After the app reloads, the role is projected onto a session row only when every private binding fact still matches one current process. A missing or reused process leaves the coordinator offline and decorates no row — the role never migrates to a matching label or to the most recently active assistant.

A guarded reconnect — POST /v1/orchestrator/coordinator/rebind — moves that same stable role to one exact current process. It is a closed three-field compare-and-swap: the expected coordinator id, the expected generation, and one live session id, all taken from the most recent read. Either mismatch refuses and asks the caller to refresh. An exact current binding is idempotent. Any different candidate is accepted only when one complete current scan contains the candidate and does not contain the old binding. If the old binding is present, live takeover is refused; if the scan is incomplete, the answer is that liveness is unknown — the app refuses to convert absence of evidence into proof of death. The same applies to a scan that predates the current binding: a pre-binding snapshot cannot disprove a newer tuple. A clock that moved backwards fails closed rather than making stale evidence look fresh.

What it reads

GET /v1/orchestrator/coordinator returns durable presence plus Bearings: one deterministic snapshot over existing session metadata, active task records, pending landings and open coordination waits. Every live session row carries exactly one closed work state — ready, working, holding, waiting_you, waiting_session, unknown, milestone_complete or work_complete — projected from those separate sources rather than stored as a second truth (see docs/session-states.md for the per-state contract and the independent owed overlay).

  • A missing or unrecognised value fails closed as unknown, never as blank idle and never as a check. An idle assistant without positive evidence — an assistant-free prompt, or its own authenticated declaration — is unknown, an absence that asks nothing of the reader, not ready.
  • Current work outranks an older receipt, because somebody can resume a lingering tab and the earlier assignment's success cannot claim that new activity is finished. An idle dispatcher with a live child is waiting_session, validated against the task's resolved root process and drawn as a quiet ⏳ child-task wait rather than triage; if the root works in parallel, working wins.
  • One check — a delivered milestone — requires either a task receipt or an explicit root-turn delivery receipt bound to the process occupying that session now. A terminal reused by a later process cannot borrow either receipt.
  • Two checks require the task-scoped, machine-authenticated and git-verified target landing described in section 12, and no unresolved wait or open handoff. Neither unstructured assistant prose, nor a progress note, nor coordinator advice can write either check.
  • Each source in the snapshot carries its own observation time, provenance and freshness. Two independent registries cannot be read transactionally together, so an incomplete inventory is marked stale rather than advertised as a complete instant.
  • The snapshot returns only opaque and terminal-neutral identifiers. No transcript, transcript path, conversation id, tty, pid or process start is ever in a response.

An ordinary root reports that narrow one-turn milestone through POST /v1/orchestrator/sessions/:terminal-id/complete during its final working tool call. The broker resolves the live terminal, assistant, tty, process start and current conversation itself; the request supplies only a bounded summary. The resulting scope:session, authenticated_session_delivery receipt means delivered, awaiting approval—never independent review or whole-graph closure. Its first idle settles it, and that terminal's next working or waiting transition consumes it, so an old check cannot return after newer unreported work. Child tabs continue to report only through their task result, and only a task-scoped verified landing can produce two checks.

Registering the role enters no task registry. It cannot change parent links, depth or caps, root keys, claim ownership, wait or landing writers, a session's state, or the evidence behind a completion receipt. The coordinator explains those receipts; it never authors them.

The restart boundary

One observer is not proof

An agent's execution sandbox may refuse or isolate loopback while the application is perfectly healthy. A refusal seen from a sandbox's loopback domain is only observer_unreachable, never app_down.

Before any restart is even proposed, that reading must be corroborated with host_listener proof — the listener and process observed from the host — and a host-network health probe, host_health. Each observer's domain and provenance is recorded with the reading it produced: sandbox_loopback for the constrained one, host_listener for the host-side one. One failed observer cannot authorize restart.

This is a stated policy boundary rather than a capability: the coordinator implements no restart and no other health-driven mutation. The guarded reconnect above is the narrow exception, and it only rebinds a provably offline role to an already-live exact process — it starts no tab, wakes no model, resumes no transcript, grants no transcript access, dispatches nothing, mutates no git, and stops or deletes nothing.

The same lesson generalises, and it is worth carrying off this page: one constrained or stale observer being unable to see something is not proof that the thing died. It is the same rule as “a session id that returns nothing may only mean the app could not prove it”, and the same rule as “never infer a file release from one clean status reading”.

A workspace_busy refusal is not a scheduling verdict

It says do not start that shared-tree dispatch. Decide in this order:

  1. Narrow or split first. If the task does not truly write every conflicting path, correct its claims or split discovery, implementation and review into separate nodes. Never narrow a claim while leaving instructions that still authorise the child to write the path.
  2. Isolate work that can start from a stable commit. If the implementation does not need the blocking root's uncommitted bytes, re-send it isolated with an explicit base. Keep the intended write set in the plan and instructions so review still has an exact scope.
  3. Wait only for a real data dependency — when correctness depends on the blocking root's unfinished version, or the eventual integration cannot be reviewed without it. Register a durable wait naming the exact path and release condition.
  4. Keep implementation and integration separate. Isolation can finish implementation while a shared path is owned; it never authorises an early merge.

21How big one task should be

The broker enforces limits. Sizing is a policy file, and it is meant to be edited.

~/.config/clawdline/dispatch-policy.md is what a machine says about how work should be handed out, as opposed to how much of it. It is read fresh on every dispatch — an edit reaches the next task, not the next launch — and copied into the DISPATCHING.md of every child that is allowed to dispatch in turn. A leaf never sees it, because rules about choosing a model are noise to a session with no such choice to make. It is truncated at a generous length, and an empty file means there are no house rules, which is a position rather than a broken setting. It ships with opinions already in it, because a file with defensible rules is one somebody edits and an empty one is a feature nobody finds — and what ships is the app's own bundled copy of that file, read when a machine has no policy of its own, rather than a second draft of the rules compiled into the binary. A missing resource means no house rules and no file written, because the first-run write never overwrites and an empty file created by a bad read would be permanent.

What the shipped file says, and why:

Should this be dispatched at all?

The measurement is sharp in both directions: on work that splits into independent pieces, several agents beat a single one substantially; where every step depends on the last, every multi-agent arrangement tested was worse, because the handoffs break a chain that needed to stay whole. So the test is one sentence: can this be cut into pieces that need not talk to each other, and joined at the end?

When the answer is no, that is a recommendation and not a refusal. Give the reason in a sentence, ask, then do whatever they answer — their yes settles it, and what is owed is the reason once, before the work starts.

Shapes that look dispatchable and are not: diagnosis (every step is chosen by what the last one found), dozens of small parallel jobs, anything on a path where somebody is waiting, agents that need to talk back and forth, output a program has to parse, and work smaller than its own briefing — which does not vanish, it accumulates.

One task is one reviewable slice

  • A dispatchable node normally carries its production change, red-before-green tests, the documentation that goes with it, and its own verification, through one sustained session. Keep the implementer there until the slice is mature; new discoveries go to that session, not a new tab.
  • Never open a session for one small change. Small items pool, and the pool empties when five are waiting, or they are together worth more than about half an hour, or one of them blocks a landing or somebody is waiting on it — and no item sits longer than a day, otherwise “accumulate” quietly becomes “never”. One task carries the whole batch, its claims are the union of what it writes, and its instructions list the items separately so the result can report on each.
  • A batch is a legitimate review target in its own right: a reviewer reads the whole batch boundary in one pass, exactly as it reads one feature.

Pick a shape, and tell every node the whole graph

  • Split and join — independent pieces gathered by cheap leaves, one stronger node joining and judging. The default for research, audits and surveys.
  • Build then read — for code, or a decision somebody acts on. Never the same node or session.
  • Decide then do — one node plans touching nothing, a person passes it, a second implements. The value is the gap in the middle, where a person can still say no cheaply.
  • Batch with takeover — one mechanical change across independent modules, one node each; a dead node leaves its state on screen for a person to finish by typing.
  • Candidates — one problem, several differently-instructed nodes, a person picks. No judging node: what is compared is taste.

Breadth before depth — two children splitting a job beat one that hands half of it on. Stagger dispatches by half a minute or so rather than firing them together. And say when you did it yourself: a summary that reads as though dispatched sessions did work they never started is worth less than an honest one, because whoever reads it is deciding how much to trust the result.

Somebody has to check the work

Every graph producing code, or a decision anybody acts on, ends with a node whose only job is to find what is wrong with it — reading a complete feature or a complete batch, never a fragment, and returning the whole finding set in one pass.

  • It did not help build the thing. A model judging its own output misses a large fraction of its own drift, structurally: a judge favours text that looks likely to it, and its own output is exactly that by construction.
  • A different assistant helps and does not solve it. Where review really matters, use several, complementary.
  • Name the paths it may read — the exact directories, and for a batch every branch and head. Ask for a verdict with receipts: worst first, is it safe to ship, every finding naming the passage it rests on. A verdict without sources is the shape a hallucinating judge produces.
  • The finding set is written down and reported before a single byte is repaired. A repair made while the findings are still in the reviewer's head buries the judgement somebody needed to see. Once a reviewer has edited production bytes its verdict is spent — that repair is a delivery, and the focused diff and exact-tree acceptance belong to the root. It repairs only what does not change the design; a design-changing correction goes back to the implementer's session, where the reasoning behind the code still is. Never one task per finding.
Which assistant, which model

Broadly: one assistant for making something you then look at — code, an image, a build driven to green, mechanical edits across many files — and the other for reading and judging: a diff, why something behaves as it does, prose. Use the cheapest model for mechanical single-source work where being wrong is obvious, the middle one for a leaf with judgement in it, and the strongest for a decision somebody will act on without checking, or for any synthesis of several children's answers. Name a model only when the default is the wrong size, and say why in the plan.

22What is kept, and for how long

The promise is the one /tmp always made, made explicitly.

  • Task directories for terminal tasks are removed a day after they finished; handoff packages and their envelopes go a day after they were created. The registry keeps its most recent 200 task records.
  • A pending landing exempts a task directory from that sweep, because a root that has not landed may still need the child's receipts. Pending landing rows are likewise exempt from the record cap.
  • work/ has a shorter, separate life — section 15.
  • Artifacts are in /tmp and they are not yours to keep. If a child produced something worth having, copy it out.
  • A finished child's tab lingers for a few minutes by default so somebody can read what it did, then closes; the deadline is written down and survives a restart, and whether that tab is still the child's is asked again of a fresh reading. A timed-out task keeps its tab regardless, because whatever went wrong is written on that screen and closing it would throw away the only copy. A spawn failure that never reached briefing is the exception and closes at once: nothing of the task is on that screen, and each dead tab is a live assistant holding a slot — while the usual reason for failing to reach a prompt in the first place is too many sessions starting at once.
  • Isolated checkouts follow a fail-safe policy of their own. An empty clean checkout still on its task branch is removed with that empty branch when the tab closes; after a day a clean checkout with commits is removed while its branch is kept indefinitely; any dirty checkout, moved head, missing branch or unreadable git fact is kept. Removal always goes through git rather than deleting the directory. The one-day promise does not extend to branches: Clawdline never automatically deletes the only copy of committed work.

Every state change also goes out on the event stream, which is how a watching interface finds out without asking. And when a task finalizes, the broker looks for the root's terminal and types one compact structured line into it — a single-line envelope with a version, a kind and a closed set of fields, so that both terminal multiplexers preserve it byte for byte. Recognition is strict and whole-message only: any stray newline, extra key, unknown kind or quoted lookalike is not partly interpreted, and stays visible as ordinary text. One delivery attempt, and a failure is logged rather than retried, because the second copy of a notification is worse than none. A machine that would rather poll can switch those lines off entirely.

A session report is not one of those broker notices. A live Claude or Codex session may address another through machine-token-only POST /v1/orchestrator/messages. Clawdline resolves the source against the current terminal/process identity and types a separate versioned <clawdline-message> envelope. App and Web draw it as Clawdline ↔ source session, restore the body's Markdown and never attribute it to the person. Plain /send, hand-written prefixes such as [a0939bac name], and === headings remain ordinary user prompts; the reader does not guess identity from prose. The closed role and kind inventory is in messages.md.

23Later: the same protocol, elsewhere

Everything above is one machine talking to itself. The shapes were chosen so that it does not have to stay that way.

task.json, result.json and the routes carry no reference to a terminal, a tty, or a local path that could not be a path somewhere else. The only genuinely machine-local thing in the design is how the credential is established — a mode-0600 file that proves “a process running as this user” — and that is one function, not a protocol. A hosted version would serve the same JSON at the same paths, with an account key in place of the token file and a workspace in place of a directory on your disk; a root session would not be able to tell the difference beyond the base URL.

In the same spirit, isolation: "worktree" is a workspace-shape contract — a clean independent checkout whose delivery is a branch — not a demand that a broker invoke one particular command. An implementation may use a clone, a container or a snapshot. The task says what is requested; the record says what the broker actually did.

Nothing here depends on that happening. It is written down so that the local version does not accidentally make it impossible.

This page is the current contract, not a record of a moment. When Clawdline's task, handoff, landing, claims, file-wait, session-message or cross-session notification semantics change, this page changes with them, in the same line of work — a protocol change is not finished while the page still teaches the previous behaviour. The routes in full, with exact request and response shapes, are in the API reference that ships beside it.
