# 這套工作系統是在幫我們，還是在擋我們：拿一天的真實使用審它的設計

> **判準是使用者 2026-09-20 的原話**：「讓你們工作起來有一個流程，不知道做什麼的時候可以去看這些資訊，
> **不會忘掉該做什麼**；使用者要看你們做的東西的時候，**有個視覺化的方式可以理解現在的狀況**。
> **這整個系統跟流程應該要是輔助跟幫助，而不是阻礙跟規則。**」
>
> **依據**：本 repo `4d32f32` 的程式，加上 2026-09-20 19:50–20:05 對執行中的 daemon 做的唯讀 GET
> （`/v1/work/*`、`/v1/orchestrator/{coordinator,inventory,tasks,…}`、`/v1/board`、`/v1/timeline`、
> `/v1/orchestrator/usage/verification-ledger`），與同一份 checkout 的 `git` 查詢。**沒有任何寫入。**
> 整合 root 提供的每一個數字都自己重量過一次，不一致的寫在 §1.3。

## 0. 三十秒版本

1. **這套設計大致是對的，不要重寫，也不要重切四個物件。** 今天失敗的每一件事都不在物件裡面，
   而在物件之間的關係上：一本沒有鐘、沒有讀者的帳（落地帳），跟一條從來沒被接起來的線（派工 → 看板）。
2. **「不會忘掉該做什麼」今天靠十五個機制，其中六個會擋在你的路上、四個會推到你面前、五個等你自己來看。**
   今天說謊一整天的那一本，剛好是「等你自己來看」裡**唯一沒有鐘**的那一本（§2.2）。
   同形狀的還有兩個：摘要只存不送、完成通知裡一個永遠是 `0` 的欄位。
3. **「幫到我」與「擋到我」的分界不是嚴格度，也不完全是時機。** 證據是：使用者列在兩邊的第 4 條與第 1 條
   **是同一段程式**（`proveDelivery`）。差別在三件事：**閘門擋的那個動作還改不改得動、拒絕裡有沒有寫著怎麼改、
   以及知道了有沒有當場說**（§3.2）。四個「擋到我」裡有三個根本不是拒絕，是沉默。
4. **視覺化缺的不是新頁面，也不只是接線：要先減一條死掉的鏈，再加一頁。** 舊看板的 JSON 已凍結、沒有寫入者，
   卻被畫成活的頁面，而專案時間軸掛在它下面；落地帳則是全 console **一個畫面都沒有**的東西（§5）。
5. **GitHub 那一刀的判準仍然成立，但順序要反過來**：今天的失敗不是「issue 不知道看板」，是
   **「commit 不知道任何事」**——所以先做「綁定寫進 commit」，再做「連結到 issue」（§6）。

### 1.2 「19 筆全錯」成立，而且比使用者想的更糟

19 筆全部是 `pending_live`，年齡 3.9–5.6 小時（17 筆）與 30.5、30.6 小時（2 筆）。
我拿 `/inflight` 逐列去比它的交付分支：

| 交付分支 | 幾列 |
|---|---:|
| `head == base`（分支上沒有任何 commit） | **17** |
| `head != base` | 1（在協調者那一次讀取之後才結束的） |

原因在簡報產生器：`internal/app/orchestrator/brief.go:159` 對 **claude** child 寫的是
「**Commit early and often**，分支就是交付」，對 codex child 才寫「不要 commit」。整合 root 整天用任務
指示覆寫了前者（「不要 commit、改動留在 worktree」），於是每一個 claude child 的分支都停在 base 上。

**接下來這一段才是真正的設計問題。** 對這 17 列，三條出口現在是：

| 想記的 | 會發生什麼 | 程式 |
|---|---|---|
| `landed` | 409 `unverified_landing` / `nothing_delivered`——「分支沒有帶任何東西超過它的 base」 | `landing.go:168-173` |
| `nothing_to_land` | 409 `wrote_to_repository`——「**這台 Mac 沒有它 checkout 的 commit 數，而未知不是許可**」 | `lifecycle.go:372`、`437-469` |
| `abandoned` | **接受**，而且是假的（工作確實做完了、也確實併進去了） | `lifecycle.go:377-380` |

`/v1/orchestrator/inventory` 印出來的就是這個：`unlanded` 17 列、`do: land_or_abandon`，
其中 16 列的 `why` 一模一樣是「this Mac has no commit count for its checkout」，另一列是
「its landing obligation already names the target」。**每一列唯一被接受的答案都是唯一不真的那一個。**

為什麼是「未知」？因為 worktree 目錄已經被刪掉了（我實際去 `ls` 過，17 列裡抽查的那個目錄不在了），
`dirExists` 為假就走 `reclaimedDirty`，而那是 broker 自己的回收 sweep 才會留的紀錄——目錄不是它收的，
所以沒有那一列，`dirtyKnown` 就是 false。**證據存在一個別人可以刪掉的目錄裡，而帳本沒有留副本。**

**這是一個可修復性問題，不是嚴格度問題。** 同一個閘門在交付當下是對的（那時 worktree 還在、改動還在，
root 只要進去 commit 一次就過了），在四小時後就變成一個沒有真答案的閘門。

### 2.2 今天失敗的那個形狀，精確是什麼

不是「等你來記」，因為 C1–C3 也都要你來看，而它們今天沒有騙人。
**真正的形狀是「有帳、有年齡、沒有鐘、也沒有讀者」。**

我在 `internal/` 底下把每一個 `LandingPending` 的使用點都讀過了：`coordinator.go:342` 數它、
`landing.go:232` 判它現在是誰欠的、`notice.go:95` 在通知裡提一句、`owed.go:53` 在關閉時擋、
`inventory.go:328,358` 把它分區。**沒有任何一處讀它的年齡。** `age_seconds` 被算出來、被印出來，
然後沒有任何規則會因為它變大而做任何事。**這是這套系統裡唯一一本這樣的帳。**

**同形狀的還有兩個，都是自己找到的：**

- **摘要只存不送（缺口 3）。** 而且今天這一則要到明天 00:00 才會存在——**日報永遠只能講昨天**，
  對一天內發生 44 次派工的機器，它結構上無法參與當天的任何一個決定。
- **`noticeBody.outstanding` 這個欄位從來沒有人寫。** `internal/app/orchestrator/notice.go:65` 宣告了
  `Outstand int \`json:"outstanding"\``，全 repo 只有這一處出現過這個名字——`NoticeWire` 組 body 時沒有填它。
  所以每一封完成通知都送出 `"outstanding": 0`。**一個永遠說「你沒有欠任何東西」的欄位，
  比沒有這個欄位更糟**：它把「沒算」印成「沒有」，正是 §1.3 第 1 點那個病的另一個實例。

### 2.3 決定（→ §8 的 W1-a、W1-b、W2）：每一本帳都要有一個鐘，而鐘的動作是「換一個人問」

**W1-a（當場說）。** child 結束的那一刻，broker 已經去問過 git 分支的 head 了
（`landing.go:74` `settlementHead`，寫回 `dispatch.go:928-934` 的同一筆交易）。
所以在那一刻，「這條分支等於它的 base」是**已知**的。要做的是：

1. 把那個事實寫進 `Landing` 的 `note`（或一個新欄位），**讓證據不再只活在那個會被刪掉的目錄裡**；
2. 把 B1 那句話換掉。現在的那句是
   「claimed work may still be in the shared tree; **mark landing pending** so other roots can see it」
   ——而它已經是 pending 了，這句話要求的是一個空動作。換成說出當下唯一還有用的那件事：
   *這個交付的分支是空的；現在進去 commit 一次，或者這筆帳之後只剩 `abandoned` 一條路。*

**代價**：通知那一行變長；`Landing` 多一個欄位與一次 migration。
**為什麼是這一刻**：這是「修得動」的最後一刻——worktree 還在、改動還在。四小時後同一句話只是帳單。

**W1-b（給落地帳一個鐘）。** 一筆 `pending` 的落地超過 N 小時（建議 12，跨得過一個晚上、短於一個工作日），
**變成一筆提議**，不是自動結案。理由：
- 自動結案會製造第二個「做完了」的真相來源，違反 D01，也正是舊版 345 張「證據上做完、狀態沒動」的來源；
- 提議已經有全套的節流、退場與稽核（PT-1～PT-4），不必發明新東西。

**一定要做的節流**：**同一個理由的多列合成一筆提議**，不是一列一筆。
證據就在這台機器上：規則提議曾經因為「一次派工一個問題」在一天內生出 23 筆長得一模一樣的卡，
沒有一筆被回答（`work-system.md` PT-3）。19 筆各自成卡會原地重演一次。

**怎麼驗**：造一個 worktree task，讓它的分支停在 base、結束、把 worktree 目錄刪掉；
跑過門檻之後 `/v1/work/proposals` 恰好多一筆、內容含「幾列」與「同一個理由」，再多結束一個同樣的 task
不會變成第二筆。**每一條都要能失敗。**

**沒有選的兩條**：
- **在 child 結束時就擋住交付**——拒絕一個已經做完的交付不會讓工作回來，只會讓 child 死在手上拿著成品。
- **讓 broker 自己去 commit 那些改動**——那是 daemon 代替人做不可逆的事，而且它不知道那些改動要不要進去。

| 幫 3 | 派工前 `stale_inventory` | **還沒發生的**那個動作 | ✅ | ✅ **把整份盤點附在拒絕裡** | ✅ | 做對了 |

| 擋 1 | 落地帳四小時後才回饋 | **四小時前**的那個決定 | ❌ | ❌ 指向錯的事實（§3.2） | ❌ | 晚了四小時 |
| 擋 2 | GitHub issue 跟看板沒接 | **沒有閘門** | — | — | ❌ | 沉默 |
| 擋 3 | 派工不說它服務哪一列 | **沒有閘門** | — | — | ❌ | 沉默 |
| 擋 4 | 協調者不把不確定傳下去 | **沒有閘門** | — | — | ❌ | 沉默 |

**第一件要注意的事：幫 4 與擋 1 是同一段程式。** 同一個 `proveDelivery`、同一個拒絕碼。
所以「嚴不嚴格」不可能是變數——它在兩列裡一樣嚴格。

**第二件：時機也不是全部。** 擋 1 的拒絕發生在「你記帳」那一刻，跟幫 2、幫 4 一模一樣，都是
「你正在做的那個宣稱」。時機相同，結果相反。

### 3.2 那三個變數，就是設計原則

**G1——閘門要擋在那個還改得動的動作上。**
幫 1、2、4 擋的都是**正在發生的錯誤本身**，你退一步就對了。擋 1 擋的是一個宣稱，
而造成它失敗的決定（「叫 child 不要 commit」）在四小時前、二十幾次合併之前就下完了，
證據（worktree 目錄）也已經被刪掉。**擋住一個沒有回頭路的動作，那不是閘門，是帳單。**

**G2——拒絕裡要寫著怎麼修，而且要指向對的事實。**
幫 3 是全系統最好的一條：它**把整份盤點附在 409 裡**，所以修正是一次往返。
擋 1 的拒絕反過來：`"this Mac has no commit count for its checkout, and an unknown count is not permission"`。
我讀了 `landingAdvice`（`inventory.go:379-400`）——那一句由 `!commitsKnown || !dirtyKnown` 觸發，
而此刻 unknown 的是 **dirty**（worktree 沒了），**不是 commit 數**（分支還在，數得出來，是 0）。
**訊息把讀者送去看一個沒有問題的東西。** 這是一個真的、可修的缺陷，不是措辭問題。

**G3——知道了就要當場說，而且要說那件事。**
系統在 child 結束的那一刻就知道分支是空的，也有一個管道（完成通知），**兩個都有，卻把那一句花在一個空動作上。**

**合起來一句**：
> **一條規則，只有在「它擋住的動作還改得動」而且「拒絕裡就寫著怎麼改」的時候，才是幫助。
> 否則它不是閘門，是帳單。而最擋人的從來不是嚴格的規則，是沉默。**

### 3.3 用這條原則重讀那四個「擋到我」

三個是沉默，不是規則：**擋 2、擋 3、擋 4 根本沒有閘門。**
使用者感覺到的「被擋」，實際上是「沒有人告訴我」——這跟「規則太嚴」是相反的病，
而且**治法也相反：要加規則，不是減規則。** 這一點很重要，因為「應該是輔助而不是規則」
很容易被讀成「少擋一點」，而今天的證據說：**該擋的地方一個都沒擋，擋到的那一個是時機與訊息錯了。**

- **擋 3（派工不說它服務哪一列）** 是缺口 1，今天量到的是：44 筆派工裡 **39 筆自己開一條線**
  （`workItemId == task id`）、**2 筆指名了一列真的工作項**、**3 筆什麼都沒帶**。
  所以「看板不能當進度看」不是 CM-2 的代價，是**這條線從來沒有被接上**。
  CM-2 說的是「session 不能自己往你的看板上放東西」，它**沒有**說「派工不必說它在服務哪一列」。
  這兩件事被混在一起了。**建議（→ §8 的 W5）：不要拒絕（那會擋住做事），但要回一個 warning，並且把它算進診斷。**
  理由是 G1：派工那一刻還改得動。

## 4. 問題三：四個物件是對的切法嗎

### 4.1 結論：是，但有一個物件在偽裝成屬性

切法的軸是**讀者**與**生命週期**，這一軸今天**沒有壞**：
看板的讀者是人、待辦的讀者是 session、Backlog 的讀者是做規劃的人、GitHub 的讀者在機器外。
今天每一個失敗都發生在**物件之間**，不在物件裡面。

**真正的問題是：落地帳是第五個物件，卻被存成 task 的一個欄位。**
它有自己的生命週期（`pending → landed / nothing_to_land / abandoned`，還有 `CorrectedFrom`）、
自己的閘門（`proveDelivery`）、自己的稽核（`landing.corrected` 事件），
**唯獨沒有自己的讀者，也沒有自己的鐘。**

### 4.2 一個必須說出來的重疊：待辦與落地帳是同一個事實數兩次

TD-9 寫得很清楚：落地紀錄說 `landed`／`nothing_to_land`／`abandoned`，待辦就關。
所以此刻整合 root 的 **22 筆 open 待辦 = 19 筆待落地 + 3 個還在跑的 task**。
**它們不可能互相矛盾，因此也永遠不會互相佐證。** 兩本帳、一個事實。

**這不是缺陷，是機會**：待辦已經有讀者（session）、已經有鐘（24 小時）、已經有畫面（session 頁的那一折）。
落地帳需要的每一樣，待辦都有。

### 4.3 決定（→ §8 的 W3）：不加第五個物件，給落地帳一個既有的讀者

`work-system.md` §10 的上限寫著「物件固定四個。要加第五個，先說它取代或併入哪一個」。
**我不加。** 落地帳併進**它本來就綁著的那一筆 Session 待辦**：

- 待辦那一列多帶落地的現況（`pending` 多久了、分支空不空），**一個新的升級訊號**，
  形狀跟已經有的 `cross_session`、`long_lived`、`repeated_failure` 完全一樣；
- 落地帳仍然是 broker 的事實、仍然只由 `/landing` 寫、D01 原封不動；
- 待辦的 24 小時鐘照舊，只是現在它有理由響。

**代價**：`Escalation` 多一個值，待辦的讀取要多讀一次落地狀態（同一筆 record，不是新查詢）。
**沒有選的三條**：
- **把待落地變成看板項目**——那是機器往人的看板上放東西，違反 CM-2，而 CM-2 是今天**唯一**四次都做對的規則；
- **合併看板與 Backlog**——界線是一個事實（有沒有承諾）而不是形容詞，這正是舊版 787 張卡的病因；
  今天 Backlog 是空的，證明的是「承諾」這個判準很乾淨，不是這個物件沒用；
- **把 Session 待辦拿掉**——它的讀者不是人，量級是每次派工一列（今天 44 列），上了任何人看的畫面就是雜訊。

### 4.4 那「現在是什麼狀況」呢

使用者今天問了三次。**今天的正確答案散在：看板（11 列，全部已結束）＋ 待確認（5）＋ 待落地（19）＋
還在跑的 task（3）。** 前兩個有畫面，後兩個沒有。這是 §5 的題目，不是切法的題目——
**切法沒有讓答案變散，缺畫面才有。**

## 6. 問題五：GitHub Issue 這一刀

### 6.1 `github-issues.md` 哪裡對（我複驗過的）

- **「本機程式裡沒有任何 GitHub 用戶端」**：`internal`、`cmd` 底下 `api.github.com` **0 次命中**。成立。
- **判準「讀者在這台機器以外的才搬」**：成立，而且是這份文件最值錢的一句。
- **§5.2「綁定只存在 broker 的 task 紀錄裡，git 裡看不到」**：成立，而且今天比它寫的時候更嚴重——
  44 筆派工裡 39 筆自己開線、2 筆指名、3 筆沒帶（§3.3），而 git 那一側 17 條交付分支是空的（§1.2）。
  **今天兩個方向都沒有綁定。**
- **§6.4 不做雙向同步的四個理由**：仍然全部成立，`unconfirmed` 會在沒有人的情況下關掉一個公開 issue 這一條尤其。

### 6.2 哪裡過時了——是一天，不是半年

先更正題目的前提：`docs/github-issues.md` 上一次寫入是 **2026-09-19**，`docs/work-system.md` 是 **2026-09-20**。
**那份分析只有一天大**，所以「因為這半年的實作而過時」不成立。過時的是這一天的四件事：

1. **§5.1 說 `closed_reason` 有四種**（landed／accepted／unconfirmed／dropped）。
   現在是**五種**——`board_items` 的 CHECK 已經含 `done_elsewhere`（`adapters/store/work.go:54`）。
   這一條**加強**了它自己的建議：`done_elsewhere` 恰好就是 GitHub 的「由人確認的 completed」，
   證明「學 `state_reason`、不學 labels」是對的；而且它給了 §5.7 的 `duplicate` 一個現成的樣板
   （同一個 CHECK、同一種 rebuild migration、同一組具名拒絕碼）。**§5.7 現在是一個複製貼上大小的改動。**
2. **§2 的「提議」那一列寫在 `withdrawn` 之前。** 現在提議有第三種結束方式，而它問的是
   **「這個問題還成不成立」**——GitHub 完全沒有這個概念（它的 issue 可以開好幾年）。
   今天的數字證明它有用：33 筆裡 28 筆自己退場了。**這一列應該從「留著」改寫成「我們在這一格比 GitHub 強」。**
3. **§2 的「Backlog」那一列寫在 PT-9 之前。** Backlog 現在多了一個來源（child 的 leftover → 提議 → Backlog），
   此刻 5 筆 pending 裡有 3 筆正是這種。
4. **§1.2「公開 repo 今天 0 個 issue」**：使用者今天開了一個。我沒有連網查證（§1.3）。

### 6.3 決定（→ §8 的 W7 與 W8）：把順序反過來——先把綁定寫進 commit，再談連結 issue

`github-issues.md` §8 的順序是：①issue form → ②`duplicate`／短編號 → ③`link`/`unlink` + `Fixes` → ④之後。
**我建議把 §5.2 從第 ③ 步裡拆出來，提到最前面，而且跟 GitHub 脫鉤。**

理由是今天量到的，不是推論：
- 今天的失敗不是「issue 不知道看板」，是**「commit 不知道任何事」**。整合 root 手上有 67 顆今天的 commit，
  沒有一顆說得出它為了哪一列工作，所以 19 筆帳只能靠他的記憶去對。
- `Fixes owner/repo#N` **只對有 GitHub remote 的公開 repo 有用**。而這份文件自己量過：
  Claude 44.3%、Codex 27.6% 的工作不在公開 repo；**這個 repo 此刻根本沒有設 remote**（我跑過 `git remote -v`，是空的）。
  所以先做 `Fixes` 等於先做一個今天在這裡用不到的東西。
- `Clawdline-Work: <work_id>` 這個 trailer（§5.2 自己提過，放在附帶條件裡）**在私有 repo、沒有 remote 的
  repo、以及這個 repo 上都能用**，而且它正好是落地驗證此刻拿不到的那個東西：一個寫在交付物本身、
  不會隨著 worktree 被刪而消失的綁定。

**所以順序改成**：
- **W7**：落地時 commit 訊息帶 `Clawdline-Work: <work_id>` trailer（私有／無 remote 的 repo），
  公開 repo 另外帶 `Fixes owner/repo#N`。**隱私條件照 §5.2 原文**：`work_id` 不進公開 repo 的 commit。
- **W8**：`link`／`unlink`（`github-issues.md` §6.2 原封不動），排在 W7 之後。

**代價**：root 的落地步驟多一行；trailer 是慣例不是強制，漏了只會少一個綁定（G1：漏的那一刻還改得動——
落地閘門讀得到 commit 範圍，可以提醒，**不擋**）。
**沒有選的**：把 `work_id` 寫進公開 repo 的 commit（隱私守衛把真實 id 當私人資料）；
先做 issue form（它不用寫程式，隨時可做，但它解不了今天任何一個問題）。

### 做了什麼

### 一處跟 §5.2 不一樣，理由寫在這裡

§5.2 的表把「交了還沒記帳」那一塊指到 `/v1/orchestrator/inventory` 的 `unlanded`。
**落地的是 `/v1/orchestrator/landings`。**

`inventory` 是**單一 repository** 的（`?project=` 是必填，沒帶回 400 `bad_request`）。這一頁是
給手機看的、問的是「這台機器現在什麼狀況」，另外兩塊也都是整台機器的。要它變成單一 repository
只有兩條路：讓頁面挑一個 repository，然後把那一個的列當成這台機器的全部欠帳——**那就是「讀不到
畫成 0」的同一個錯，換一種拼法**；或者讓手機自己列出所有 repository、逐一去打、自己合併——
那是把一個 join 放到 relay 的另一端。

`landings` 是整台機器的、沒有參數、每次讀都重新推導、不存任何東西，而且它本來就帶著三個
`BearingsSource`——`sessions`、`tasks`、`landings`——所以「每一塊印出自己那個來源的 freshness」
這條硬規則在它身上是原生的，不是加上去的。§5.2 要的「每列的 `do` 與 `why`」在這條路上是
`obligation`（欠的是誰、現在是什麼意思）與 `ownership.reason`（那個人最後被看到在哪裡），
再加上新的 `settlement`。

`inventory` 沒有被改掉也沒有被取代：它仍然是派工前要讀的那一份，仍然是 `409 stale_inventory`
帶回來的那個 body。
