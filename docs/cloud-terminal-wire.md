# Cloud terminal wire

This is the terminal wire for a paired viewer. `api/v1/terminals.schema.json` remains the local HTTP contract. Cloud terminal messages use the same terminal frame, lease, input and paste shapes inside end-to-end encrypted envelopes. The Cloud control plane and relay see only envelope metadata and ciphertext. The API terminal authority stays disabled unless its deadline-bound trial gate is open; the relay has an independent deadline-bound terminal gate. A viewer needs `send_prompt` and a machine-local pairing pin, with no separate terminal grant.

## Channels

| Channel | Class | Publisher | Recipient | Relay retention |
|---|---|---|---|---|
| `termi/<machine>/<viewer>` | `ctl` | The named viewer with `send_prompt` | The named registered machine | None |
| `term/<machine>/<viewer>/<connection>` | `stream` | The named machine | The named viewer with `send_prompt` | Latest complete ciphertext frame for this connection only |
| `termd/<machine>/<viewer>/<connection>` | `stream` | The named machine | The named viewer with `send_prompt` | None; never cached or realigned |
| `termr/<machine>/<viewer>/<connection>` | `ctl` | The named machine | The named viewer with `send_prompt` | None; never realigned |

The relay checks account, role, `send_prompt`, token device, channel machine and viewer segments at publish, subscribe, fanout, realign and ingest. A `termi` target must be a registered, unrevoked machine in the same account. A machine only publishes its own `term`, `termd` and `termr` channels. A viewer only publishes its own `termi` channel and subscribes to its own `term` and `termr`, with optional `termd`. Read-only viewers have no terminal right. A connected socket whose `send_prompt` is revoked loses terminal publish and receive rights within five seconds, including when it sends nothing. Other Cloud channels keep their existing capability rules.

The connection segment is a random tab connection identifier (base64url, 22 characters). Machine and viewer segments are their paired device IDs. The complete channel is at most 300 ASCII bytes; a sender refuses an ID combination that exceeds this bound before sealing. The connection is distinct from the stable browser tab `client` that holds a terminal lease. A new network connection uses a new segment and a new key even when the lease continues. Each viewer may reserve at most two connections, allowing one active connection while a rekey connection opens. The first terminal subscription reserves a slot; both exact `term` and `termr` subscriptions must be confirmed within fifteen seconds or the reservation expires. Terminal subscriptions use a separate quota from ordinary Session subscriptions. The machine may publish a frame only after its authenticated metadata registration activates that reserved connection.

## Encryption and key state

### Observed-screen deltas

A viewer may subscribe to `termd` in addition to `term` and `termr`. Only the latter two subscriptions are required for legacy connection admission. After `termd` is confirmed, the viewer may send `frame_delta_v1:true` in the `open_connection` or `rekey_connection` body. The machine echoes that flag in a successful connection receipt only when it enables deltas. A viewer that did not request the flag, or did not verify the echo, accepts complete `term` frames only. The first frame of every connection is complete.

The `termd` plaintext is `{v:1,type:"terminal_frame_delta",terminal_id,connection,frame_seq,base_seq,base_rev,captured_at,rev,at,cols,rows,dead,cursor,modes,changed_rows:[{row,line}],screen_hash}`. `frame_seq` advances across both rails. The base is the last logical screen whose frame was settled as delivered after viewer observation. `changed_rows` contains strictly increasing zero-based row indexes; all other lines come from that base. `cursor` and `modes` are complete values. `captured_at` and `at` are equal Unix seconds. `screen_hash` is lowercase SHA-256 over a big-endian uint32 line count followed by each line's big-endian uint32 UTF-8 byte length and exact UTF-8 bytes. Values that cannot fit in uint32 force a complete frame.

The machine keeps one observed base and at most one pending candidate. A pending frame defers later captures; the next read retries the newest screen. Only delivered settlement promotes the candidate. Failure retires the connection. A resize, alternate-screen transition, new key, missing base, periodic calibration or delta no smaller than the complete JSON frame sends a complete `term` frame. The complete and delta rails share one in-flight observation window. The relay must use the same connection key for both, and must never put a `termd` envelope in its complete-frame cache or realign it. A viewer checks signature, route, key, nonce, outer sequence, base sequence and revision, dimensions, alternate-screen state, row order and bounds, reconstructed hash and freshness before drawing or acknowledging. Any mismatch discards the connection and requires a new key and complete first frame; input is not replayed.

Every envelope retains the existing exact ten fields: `v`, `ch`, `seq`, `ts`, `class`, `key_id`, `nonce`, `ct`, `sender`, `sig`. `seq` is the signing device's monotonic envelope sequence, independent of terminal input `seq`; `ts` is Unix milliseconds. `nonce` is canonical base64 of 12 random bytes, `ct` is canonical base64 of AES-256-GCM ciphertext and tag, and `sig` is Ed25519 over the existing canonical signing bytes. The `termi` envelope has `sender=<viewer>`, `class=ctl` and the account content key id. `term` and `termr` have `sender=<machine>`, their channel's class and the connection's `rk-` key id (exactly `rk-` plus 22 base64url characters).

`termi` plaintext is encrypted under the existing account content key and signed by the viewer. The machine accepts its `sender` only after the envelope signature, roster capability, account and pinned public key all pass. A JSON field or HTTP header cannot choose the principal. `term` and `termr` plaintext are encrypted under the viewer's fresh 32-byte connection key carried in an `open_connection` or `rekey_connection` request. Only the named viewer tab holds that key. The machine stores it in memory and never publishes it. Key expiry is at most ten minutes.

Connection states are `opening`, `active`, `rekey_pending` and `closed`. An `open_connection` request is machine-scoped: it contains a fresh `connection`, `key_id` and base64 `key`, with no terminal ID yet. The browser subscribes to `term` and `termr` and waits for a relay `subscriptions` confirmation naming both exact channels before sending `open_connection`, `rekey_connection` or input. A missing or timed-out confirmation fails closed; the local subscription call alone is not proof. Once the machine admits `open_connection`, it registers the connection on its authenticated machine WebSocket, waits for `terminal_connection_registered`, and only then publishes frames. Registration contains no terminal ID, key or plaintext request body. The machine then returns an `open_connection` receipt on `termr` encrypted with the new key, with `result: {connection, key_id, expires_at, machine_incarnation}`; receipt `expires_at` is Unix seconds with fractional milliseconds. `machine_incarnation` is a fresh random 128-bit identifier made on each daemon start; it prevents an epoch reset after restart from looking like the old lease. Input remains disabled until this receipt verifies. A subsequent `open` or `read` response names the terminal and is followed by a complete first frame. Rekey uses a new connection and key, with an acknowledgement encrypted under the new key. Its request carries `body={old_connection:<old>}`; the machine requires that old connection to belong to the same viewer and remain live, then binds the new connection to the old terminal and client before starting its new complete frame stream after the rekey receipt settles as delivered. An unknown top-level `previous_connection` is invalid and must not be sent. The viewer keeps its old connection until the new receipt and complete first frame verify, then sends a `terminal_request` with `operation=activate_connection`, `connection=<new>` and `body={old_connection:<old>,first_frame_seq:<verified new frame sequence>}` over `termi`. The machine validates the same viewer, live old and new keys, relevant lease identity and a complete new frame with that sequence before returning a new-key `termr` receipt with `result={connection:<new>,retired_connection:<old>}`. It then retires the old connection and clears its key; the relay deletes its cached frame on authenticated retirement. The viewer unsubscribes the old channels only after this receipt verifies. A lost acknowledgement, first frame or activation leaves the old connection usable only until its expiry while its own subscriptions are confirmed. The new connection can be retried or reconciled without replaying input. Expiry disables input and requires a fresh connection. A lost new first frame or relay cache miss requests a fresh complete frame. An old key, connection, viewer, nonce or replayed envelope never becomes current again.

Connection metadata is a separate relay control frame sent only on a machine WebSocket that completed challenge and hello, never through `/v1/ingest`:

```json
{"type":"terminal_connection","request_id":"<uuid>","action":"register","machine":"<id>","viewer":"<id>","connection":"<random>","expires_at":0}
```

`action` is `register` or `retire`; `expires_at` here is Unix milliseconds and must be in the future but no more than ten minutes away. Registration cannot extend an existing connection id. The relay requires the authenticated attachment's role and device/machine id to match `machine`, the viewer's current terminal capability, and a matching paired subscription reservation. Only the machine that registered a connection can retire it. It answers `terminal_connection_registered`, `terminal_connection_retired` or `terminal_connection_refused`; each answer echoes `request_id`, `action`, `machine`, `viewer` and `connection`, and a refusal adds a typed `code`. On the same authenticated machine socket, a repeated `request_id` with identical payload replays the fixed answer; the same id with a different payload is a typed conflict. A DO restart discards this idempotency state and cached frame: the machine uses a new request id only after the viewer has re-established the paired reservation, and the viewer waits for a new complete frame. Lost retirement confirmation is bounded by expiry; a lost registration confirmation prevents frame fanout/cache. A viewer cancellation uses ordinary unsubscribe.

## Plaintext shapes

All objects use `v: 1`, reject unknown required semantics, and validate byte and nesting bounds before entering terminal service. `request_id` is unique for a request and correlates a receipt; it is distinct from the terminal input sequence and the envelope sequence.

```json
{"v":1,"type":"terminal_request","request_id":"<uuid>","connection":"<random>","operation":"open_connection","key_id":"rk-<random>","key":"<base64 32 bytes>"}
```

Other `terminal_request` operations are `list`, `open`, `read`, `capture`, `history`, `control`, `input`, `paste`, `resize`, `close`, `release_connection`, `renew_connection`, `rekey_connection`, `activate_connection` and `direct_offer` (see Direct carrier). The fixed top-level fields are `v`, `type`, `request_id`, `connection`, `operation`, and optional `terminal_id`, `project_id`, `client`, `epoch`, `seq`, `key_id`, `key` and `body`. Operation-specific `body` follows the local terminal contract: `open` has `{cols,rows}`, `input` has `{data}` with base64 bytes, `paste` has `{text}`, `resize` has `{cols,rows}`, and `history` has `{lines}`. `rekey_connection` has `{old_connection}` and may include `frame_delta_v1:true` after delta subscription confirmation; `open_connection` may include only that optional capability flag in its body. Neither adds top-level fields. `activate_connection` has `{old_connection,first_frame_seq}`. `control` with no `body.action` is a pure state query; with an action it applies the local `acquire`, `renew`, `release` or `takeover` semantics. A query must still name the stable `client` so `same_client` and holder-only `applied_through` can be computed. An input or paste carries `terminal_id`, stable `client`, lease `epoch`, `seq`, and its bytes/text inside `body`. The machine does not infer any effect from a relay `ack`.

An `ok` receipt's `result` follows the local contract: `list` returns `{terminals:[Terminal,...]}`, `open` and `read` each return one complete `Terminal` with `id`, `project_id`, `created`, `status`, `cols`, `rows` and `control`. Cloud `history` returns `{lines:[string,...],truncated:boolean,omitted_lines:number}`: chronological complete lines from the newest suffix, and an exact count of older lines omitted to fit the 8 KiB serialized receipt limit. The machine refuses a history line over 4 KiB with `terminal_history_line_too_large`, or captured output over 4 MiB with `terminal_history_too_large`; it never silently cuts a line. There is no cursor or stable history snapshot: reconnect reads the current newest suffix again. Local HTTP history retains its existing shape and behavior. The separate `terminal_frame.frame` is one complete local `TerminalFrame`; its `terminal_id` and connection identify the stream. `connection` and `key_id` are independently generated random values; equality between their random suffixes is neither required nor meaningful.

```json
{"v":1,"type":"terminal_frame","terminal_id":"trm_<uuid>","connection":"<random>","frame_seq":1,"captured_at":0,"frame":{"rev":"<digest>","at":0,"cols":80,"rows":24,"cursor":{"x":0,"y":0,"visible":true},"modes":{"app_cursor":false,"app_keypad":false,"mouse":"none","mouse_sgr":false,"alt":false},"lines":[]}}
```

A `term` cache contains only a `terminal_frame`, never a receipt, partial diff or history. `captured_at` and the nested `frame.at` are Unix seconds with fractional milliseconds, matching the local terminal contract; the outer envelope `ts` alone is Unix milliseconds. A frame above the relay's per-connection retention bound is refused before fanout so reconnect cannot falsely claim a full frame is available. Every frame is a complete screen. The browser labels the first verified frame after each open/reconnect “just synchronized”; only a later newly captured frame is “live”. A frame timestamp or beat that is stale, `machine_offline`, or `machine_stale` disables input.

The relay's server-side WebSocket does not expose a readable buffered byte count. Its terminal fanout therefore sends at most one complete `term` envelope per viewer connection while awaiting observation. After verifying and decrypting a complete frame, the viewer sends `{"type":"terminal_frame_observed","machine":"<machine>","viewer":"<viewer>","connection":"<connection>","envelope_seq":<outer envelope seq>}` on its authenticated socket. The relay accepts the acknowledgement only from that viewer attachment for its current in-flight envelope sequence. The sequence is the signed outer envelope `seq`, because `frame_seq` is encrypted and unavailable to the relay. While one frame is in flight, a newer frame replaces a single latest pending ciphertext frame; an acknowledgement releases that latest frame. An observation timeout stops terminal fanout for that connection with a typed error until a fresh subscription and complete frame, and terminal receipts and ordinary Session channels do not wait behind this queue. This acknowledgement confirms browser observation of a frame; it is not a machine operation receipt, input acknowledgement, or authority grant. The private relay records finite timeout and aggregate byte bounds beside their enforcement.

When local pin or send-permission revocation invalidates an idle connection, the machine publishes one signed, per-connection-key encrypted `termr` payload and waits for relay publish acknowledgement or typed publish failure before retiring its relay registration: `{"v":1,"type":"terminal_notice","connection":"<connection>","code":"terminal_access_revoked","machine_incarnation":"<incarnation>"}`. It has no `request_id` and is never a `terminal_receipt`. The viewer accepts it only after the normal machine signature, exact `termr` route, connection key and sequence checks, then stops input and discards the lease immediately; a mismatched incarnation also fails closed. The relay cannot read the code. If publication or delivery fails, the viewer's existing frame freshness and key-expiry rules still stop input. A terminal request that arrives while the machine still holds a registered revoked connection gets a correlated `terminal_receipt` with `status="refused"` and `error="terminal_forbidden"` and waits for its relay publish acknowledgement or typed failure before that registration is retired; host input is never applied. The machine bounds any revoked registration hold to a few seconds and never publishes another frame or accepts input during it.

```json
{"v":1,"type":"terminal_receipt","request_id":"<uuid>","connection":"<random>","terminal_id":"trm_<uuid>","operation":"input","status":"ok","result":{"applied_through":1,"duplicate":false}}
```

`terminal_receipt.status` is `ok`, `refused` or `unknown`. `read`, `capture`, `history`, `control`, `input`, `paste`, `resize` and `close` are terminal-scoped and their receipts include top-level `terminal_id`, which must match the pending request. `open_connection`, `release_connection`, `renew_connection`, `rekey_connection`, `activate_connection`, `list` and `open` are machine-scoped and may omit top-level `terminal_id`; an `open` success identifies its newly created terminal in `result.id`. A refusal carries the existing `TerminalRefusalCode` and optional `applied_through`; `unknown` means the host cannot prove whether input was applied. Relay acceptance/fanout, host application, viewer receipt and human observation are separate facts. A receipt is accepted only when its machine signature, viewer channel, connection, key id, request id, operation and, when scoped, terminal id all match the pending request in this tab. `request_id` is a fresh random UUID per request and cannot be reused by another tab or after a new connection. `termr` has no cache; after a lost receipt, a new `control`/state query reconciles the lease's `applied_through`. No client automatically resends input on timeout, `terminal_busy`, `input_gap` or `input_state_unknown`.

The hosted console adds a typed terminal transport next to the byte-for-byte copied legacy Cloud client. It needs `publishTerminal(request)` to seal/sign a `termi` envelope with the account key, `subscribeTerminal(connection, onEnvelope)` and `unsubscribeTerminal(connection)` for `term` and `termr`, and `openTerminalEnvelope(envelope, connectionKey)` to verify the machine signature, check channel/key/sequence and decrypt under the tab key. This surface must use the existing authenticated viewer socket and sequence allocator; it must not open a separate unauthenticated WebSocket or change copied legacy files. The adapter exposes relay `ack`, `machine_offline` and `machine_stale` separately from machine receipts.

Machine `list` requests use a separate bounded queue and one worker. A slow host list does not delay connection admission or input. When that queue is full, a keyed `terminal_busy` refusal is sent where possible; stateful operations retain their arrival order on the ordinary terminal lane. A request ID already in flight is refused as busy without replacing its eventual remembered receipt.

## Direct carrier

A terminal connection opens on the relay as above. When the browser and the machine can reach each other, the browser upgrades it to a **direct connection** whose screens and requests travel over a WebRTC data channel (the DC) between the browser and the machine instead of through the relay. Envelopes are unchanged: every `termi`, `term` and `termd` message on the DC is the same signed, end-to-end encrypted envelope, verified by the same rules. Receipts and notices (`termr`) stay on the relay for every connection. The relay remains the authority: a direct connection is registered, subscribed and bounded on the relay exactly like any other connection. The rationale and measurements are in `docs/terminal-direct-path.md`.

### Offer and answer

The browser creates an `RTCPeerConnection` with STUN only (`stun:stun.cloudflare.com:3478`, `stun:stun.l.google.com:19302`), creates one data channel labelled `clawdline-terminal-v1` (ordered, reliable), creates an offer, and waits for ICE gathering to complete (at most 3 s; no trickle). It then sends `operation:"direct_offer"` on `termi`, naming a live connection it owns, with body `{"sealed":"<base64>"}`. `sealed` is AES-256-GCM under that connection's key: a 12-byte random nonce followed by the ciphertext of the UTF-8 offer SDP, with additional data `clawdline-direct-offer-v1/<connection>`. The SDP (and its candidates, so the viewer's addresses) is therefore readable only by the machine, not by other account devices.

The machine admits an offer only when the sender passes the terminal authority check (`send_prompt`, pinned key, fresh roster), the named connection exists, belongs to the sender, and is not denied or expired, direct paths are enabled on this machine, the viewer has no other peer, the machine has fewer than `CloudTerminalDirectPeersLimit` peers, the viewer has sent fewer than `CloudTerminalDirectOffersPerMinuteLimit` offers in the last minute, the opened SDP is at most `CloudTerminalDirectSDPBytesLimit` bytes, and it has at most `CloudTerminalDirectCandidatesLimit` candidates. Only UDP candidates are used; candidates for loopback, link-local, multicast or unspecified addresses are dropped. `.local` (mDNS) candidates are resolved. The machine answers with a `terminal_receipt` on that connection's `termr`: `status:"ok"`, `operation:"direct_offer"`, `result:{"sdp":"<answer SDP, gathering complete>"}`. A refusal uses `terminal_direct_disabled`, `terminal_direct_unavailable`, `terminal_busy`, `terminal_forbidden` or `terminal_invalid`. The DTLS fingerprints travel only inside these signed, encrypted messages, so the DTLS peer on each side is the paired device that signed them. An older machine refuses the unknown operation with `terminal_invalid`; the browser stays on the relay.

ICE that does not connect within `CloudTerminalDirectNegotiateSecondsLimit` closes the peer. There is no TURN server: a path that needs one stays on the relay.

### DC messages

Every DC message is a UTF-8 JSON text message of one of three shapes:

- `{"t":"env","e":<envelope>}` — one whole envelope, the same JSON object the relay would carry.
- `{"t":"chunk","id":<uint>,"i":<index>,"n":<count>,"d":"<string>"}` — a piece of the JSON text of one `env` message that is longer than 16384 bytes. Each piece's `d` is at most 16384 UTF-16 code units. A sender writes all pieces of one message contiguously, in order, before any other message in that direction. The receiver joins `d` values in order and parses the result as an `env` message. A piece out of order, a piece of a different `id` before the current message is complete, a message longer than `CloudTerminalDirectMessageBytesLimit`, or a partial message still incomplete after `CloudTerminalDirectChunkSecondsLimit` closes the DC. Bounds are checked before JSON is parsed.
- `{"t":"ack","connection":"<connection>","frame_seq":<uint>}` — browser to machine only: the carrier acknowledgement of a frame (below). It carries no authority.

Browser → machine: `env` messages carry `termi` envelopes. The machine runs the same admission ladder as for the relay (channel, sender key, signature, the same replay window shared with the relay, decrypt) and additionally requires `envelope.sender` to be the viewer whose offer created this peer and the channel to be `termi/<machine>/<that viewer>`. The machine accepts `termi` for any of that viewer's connections from either carrier.

Machine → browser: `env` messages carry only `term` and `termd` envelopes of that viewer's direct connections. Their outer `seq` is a per-connection counter starting at 1, independent of the machine's relay sequence; the browser's per-connection, per-channel strictly increasing sequence check applies unchanged.

### Switching to direct

After the DC opens, the browser sends `rekey_connection` **over the DC** with body `{"old_connection":"<current>","carrier":"direct"}` (plus `frame_delta_v1` as usual), having first subscribed the new connection's `term`, `termr` and optional `termd` on the relay exactly as for any rekey. The machine refuses `carrier:"direct"` with `terminal_direct_unavailable` unless that viewer has a peer whose DC is open; it never silently downgrades. Otherwise the new connection is registered on the relay as usual, and its `ok` receipt (on the relay `termr`) adds `"carrier":"direct"` to `result`. `activate_connection` follows as for any rekey and may be sent on either carrier. From then on the machine publishes that connection's `term` and `termd` only on the DC; the browser drops `term`/`termd` for a direct connection that arrive from the relay, and for a relay connection that arrive from the DC. Rotating a direct connection's key is a `rekey_connection` with `carrier:"direct"` whose old connection is the current direct one.

A peer belongs to one connection. It is created by an offer naming a relay connection; when the machine accepts `activate_connection` for a direct connection, the peer moves to that connection before the receipt is sent. When the connection that owns the peer is retired and no direct rekey from it is pending, the peer closes. When a peer closes, all of that viewer's direct connections are retired.

### Flow control

One frame is in flight per direct connection, as on the relay. After verifying, decrypting and drawing a frame from the DC, the browser sends `{"t":"ack","connection":…,"frame_seq":…}`; the machine settles the frame on it (instead of on a relay `delivered` acknowledgement) and may then send the next. The browser does not send `terminal_frame_observed` to the relay for DC frames. No ack within `CloudTerminalDirectAckSecondsLimit` retires the connection and closes the viewer's peer, even when a direct rekey not yet activated leaves the peer owned by the connection it replaces: otherwise the browser would wait on a channel the machine no longer feeds.

### The relay stays the authority

For each direct connection the machine publishes on its relay `termr`, at most one at a time and every `CloudTerminalDirectProbeSecondsLimit`, `{"v":1,"type":"terminal_carrier_probe","connection":"<connection>","n":<uint>}`. The browser verifies it like any `termr` payload and discards it. When the relay has withdrawn the viewer's terminal authority, released the registration (for example because the viewer's relay socket closed), or cannot deliver, the probe settles as `forbidden`/`peer_error` or `viewer_offline` instead of `delivered`, and the machine retires the connection, which closes its peer. A probe still unsettled after `CloudTerminalDirectProbeUnsettledSecondsLimit` retires it and closes the peer too. Peers belong to the machine's relay connection: when that socket ends, every peer closes with it.

Revocation known to the machine is enforced exactly as on the relay path: every request and every frame passes the terminal authority check, which requires a roster read from the Cloud API that succeeded within the last two seconds (dated from the read's start; a failed read counts from its completion), and the terminal sweep runs every second. Frames and input stop within four seconds of a revocation and an idle connection's `terminal_access_revoked` notice is sent within five.

### Fallback

When the DC closes or fails, an ack or chunk times out, or ICE fails, the browser rekeys back to a relay connection over the relay, naming the direct connection as `old_connection`; if the machine has already retired it, the rekey is refused with `terminal_invalid` (the code for an `old_connection` that is not live), and the browser opens a new connection and proves its lease as after any network reconnect. Inputs without a receipt are never replayed. A connection the browser was still rotating away from (the relay connection a direct rekey had not yet activated over) is released when the fallback connection opens, so it does not hold one of the relay's two connections per viewer. After a failed upgrade the browser waits `CloudTerminalDirectRetrySecondsLimit` before trying again for the same terminal, or `CloudTerminalDirectBusyRetrySecondsLimit` when the relay refused it with `rate_limited` or `over_capacity`: the relay's per-account terminal budget and its two connections per viewer are briefly full while a page opens. Only a tab holding the terminal's lease upgrades, because the machine activates a rekeyed connection only for the lease holder.

When the machine setting `cloud_terminal_direct` (default on) is off, offers are refused with `terminal_direct_disabled` and the browser stays on the relay.

## Lease continuity and revocation

The same tab keeps `client`, lease `epoch` and next input `seq` through a key rekey. A `control` query is read-only: it must not acquire, renew or take over a lease. Its receipt returns `{machine_incarnation, control, input_state_unknown}` where `control` is the existing `TerminalControl` including `held`, `epoch`, `holder.same_device`, `holder.same_client`, `expires_at` and holder-only `applied_through`; `input_state_unknown` is a boolean. When it is true, the viewer stops input and requires a new lease acquisition rather than trusting the high-water mark. A network reconnect may keep its lease only after a new connection has verified the same machine incarnation, `held=true`, the same viewer and client, a future expiry, the exact epoch, `input_state_unknown=false` and an `applied_through` at least as high as the last confirmed input. It then resumes at `applied_through+1`; a pending input with no receipt is never automatically replayed. Before the first complete frame of the new connection, input remains disabled even if this lease proof succeeds. When any fact cannot be proved, the viewer stops input and asks the person to reacquire a new lease epoch. Taking over or changing the tab client also requires a new lease. The host's existing per-lease high-water mark decides duplicates; the effect identity is viewer, terminal, client, epoch and input sequence, scoped to the machine incarnation.

A local pin or send-permission change revalidates leases and streams immediately. Active terminal connections need a bounded, singleflight roster/capability refresh or pushed invalidation with a two-second deadline; stale or failed refresh closes only terminal connections and refuses the next terminal request. The relay uses terminal-specific capability authority with a refresh or pushed invalidation deadline of two seconds; its general entitlement cache and the socket's original token claims cannot prove current `send_prompt`. An account with any terminal reservation or active connection schedules a terminal authority alarm at least every two seconds, even with no traffic. Concurrent refreshes share one bounded request; a delayed alarm, timeout, 429 or exhausted global refresh budget fails closed for terminal rights. It invalidates old socket attachments for terminal publish and receive within five seconds of a capability change, including idle sockets. Revocation prevents the next request from entering host typing and stops subsequent frames; an input already admitted to host typing can complete and cannot be rolled back. Its receipt or a later control query must report its effect or `input_state_unknown`. Neither path blocks ordinary Session messages.

The relay discards a connection's cached frame when an authenticated machine retirement arrives, its viewer or machine socket closes, or the connection expires. Close and rekey are E2E plaintext and cannot themselves be parsed by the relay; if a retirement signal is lost, the old encrypted cache remains bounded by the connection key's ten-minute expiry and receives no new frame. The relay enforces a per-frame bound before fanout, a per-viewer connection count including pending reservations, and an account-wide terminal cache byte bound; exceeding any bound returns a typed refusal without sending a partial frame or evicting the old complete frame. Terminal cache eviction must not evict ordinary Session channel state. Relay fanout to a slow viewer is bounded and drops or closes that terminal stream without queuing unbounded frames or delaying ordinary Session messages. The private Cloud implementation names and documents each numeric bound beside its enforcement and tests aggregate pressure as well as single-frame overflow.

## Required cross-component checks

Use an authorized viewer, a paired read-only viewer, and a revoked viewer. Verify their publish/subscribe matrix, pin/key mismatch, same-effect duplicate input, gap and full-queue refusal, host-applied/lost-receipt reconciliation, lost rekey acknowledgement, cache miss, slow socket, oversized frame, idle revocation, Cloud log/storage ciphertext-only canary, and an ordinary Agent Session send while terminal frames are flowing. The browser URL, account fixtures and origin permissions are preflight requirements before the comprehensive end-to-end round.

A list-only browser sends `release_connection` after its list receipt. The machine publishes the final keyed receipt, blocks further effects on that connection, and retires its relay registration when that receipt settles. The list can render without waiting for this cleanup receipt. This prevents repeated refreshes from occupying the per-viewer connection quota for the full key lifetime.

The browser may publish at most four numbered input or paste requests before their receipts arrive. Publication is ordered; a later key waits when the window is full. Each receipt still proves its own applied sequence. Any unknown input outcome pauses further typing and requires reconciliation; no key or paste is automatically replayed. The viewer redraws changed rows from each verified complete frame, while a resize or alternate-screen transition redraws the full frame.

When a complete frame is awaiting relay settlement, the machine defers a newer frame without advancing the watch’s last delivered revision. Its next read retries the newest full frame, so a change during backpressure need not wait for the three-second idle heartbeat. Failed relay settlement still retires the connection.
