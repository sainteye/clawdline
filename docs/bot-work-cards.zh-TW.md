# Bot 工作卡：給你看的摘要

狀態：提案第二版，等你審閱。還沒有實作任何東西。完整設計（英文）在
[`bot-work-cards.md`](bot-work-cards.md)。

第二版補上審查指出的五個缺口：一次整合好幾張卡、不是用合併而是用複製或壓成一個 commit 的落地、
驗證過之後又被還原、退回時誤傷別人的 commit，以及「開發版」「Cloud」這兩個去處其實只有 Clawdline
自己的專案才有。另外加了一個可選的「上線後驗收」步驟。

## 要解決什麼

你把工作交給幾位常駐 Bot：開發、審查、測試，最後由整合的 Bot 合併、推上遠端、裝到這台
電腦的開發版，再部署到 Cloud。這個月下來，進度全寫在聊天裡，出了幾件事：

- 想知道「這個功能現在到哪了、上線了沒」，得翻好幾個 Bot 的對話。
- 審查 Bot 退回了兩個 commit，它們還是上了 GitHub 和 Cloud。退回只是一句話，本機為了退回而做的
  還原又在一次重設時不見了，沒有任何東西擋住推送和部署。
- 「這個 commit 取代那個」「這次合併順便帶上那個」這類關係，只存在對話裡。
- 每次都要有人手動比對本機、遠端、開發版、Cloud 的版本，上線後通知原本交辦的 Bot 也是靠記得。

## 它是什麼

一張「Bot 工作卡」對應你交代的一件事。卡片是獨立的一類紀錄：不是看板項目，不算進看板的數字，
你自己建的看板項目和 Session 的用法都不變。

卡片記錄：

- **是誰授權的**：你哪一則訊息（或 Bot 轉達你的哪一則訊息）。
- **現在在誰手上**：開發、審查或整合，以及是哪一位 Bot。交接都留紀錄，不能改寫。
- **審查結果**：通過、有條件通過（寫明條件）、退回，每一個都綁定確切的 commit。
- **各個去處的實際狀態**：每一項都由系統自己去讀，附上讀到的版本和時間，不採信 Bot 的說法。
  讀不到就顯示「不明」，不會被當成完成。

## 去處：每個專案都有兩個，其餘由專案自己定義

第一版把去處寫死成四個（本機 main、GitHub、開發版、Cloud）。後兩個只有在專案就是 Clawdline
本身時才有意義，可是 Bot 會在任何專案工作。所以改成：

- **每個專案都有的兩個**：主線分支（不一定叫 main）和它的遠端（不一定是 GitHub）。
- **專案自己定義的去處**：由你在專案設定裡加。Clawdline 的「開發版」和「Cloud」就是最先的兩個
  定義，系統偵測到專案是 Clawdline 時會提供現成的設定讓你確認。
- **其他專案的卡**：只有主線和遠端，四個燈（建置、審查、主線、遠端），不會出現開發版或 Cloud。
  專案沒有遠端時，遠端那一項直接標成「不需要」並寫明原因。

去處只有你能定義、修改或移除。因為它決定「怎樣才算完成」，Bot 如果能自己定義，就能定一個
很容易達成的。

## 你會看到什麼

- **看板多一區「Bot 工作」**，可以依 Bot 篩選。每張卡先有四個燈：建置、審查、主線、遠端，
  後面接這個專案自己的去處（Clawdline 是開發版和 Cloud，所以一共六個）。綠燈代表已驗證，
  滑過去看得到版本和時間；灰色代表不需要或已被取代；黃色是還在等，或是「Bot 聲稱、尚未確認」；
  紅色是被擋下、被退回或已被還原；問號是讀不到，並寫出原因。
- **需要你的卡放在這一區最上面**：Bot 在等你回答、被退回的東西已經上線、做好的東西後來被還原，
  或有東西等你確認。
- **Bot 聊天室上方那條派工列**，會把同一張卡的工作排在一起，一行就看得到燈號。
- **手機和 Cloud 看到同一份資料**，內容一樣經過加密傳送。

## 一次整合好幾張卡

整合的 Bot 常常一次把好幾個功能合在一起落地、部署一次。所以多了一筆「整合批次」紀錄：
整合的 Bot 把幾張卡（最多 16 張）放進同一批，派出一個整合工作。

- 落地一次、部署一次、檢查一次，這一批的每張卡都用同一份讀數，不會每張卡各跑一遍。
- 每張卡仍然各自判斷：有一張的內容沒有真的進到這次落地，它就留在「整合中」，不會拖住其他張。
- 交接和完成通知都合成一則，列出這一批的卡，不會一張卡吵一次。
- 落地之前可以把其中一張退回給開發的 Bot，其他張照常進行。

## 「有進去」要怎麼證明

整合不一定是合併，常常是把 commit 複製過去，或把好幾個壓成一個。系統依序用三種方式確認：

1. **原本的 commit 就在主線的歷史裡**：系統自己能證明。
2. **內容一模一樣、只是換了 commit 編號**（乾淨的複製或重排）：系統自己能證明，用的是現有
   派工落地已經在用的同一種比對。
3. **被壓成一個，或複製時手動解過衝突**：這種情況 Git 無法證明，只能靠人說。這時燈號是黃色，
   標明「某某 Bot 聲稱」，卡片**不會因為這句話就完成**；要原本審查的 Bot 對實際落地的那個
   commit 再看一次並通過，或由你確認。確認之後燈變綠，但仍保留「聲稱」字樣。

## 驗證過之後又被還原

東西合進主線後就算被還原，在 Git 的歷史裡它還是「有進去過」，光看歷史燈會一直是綠的。所以：

- **乾淨的還原（`git revert`）系統認得出來**，會把卡片標成「已被還原」，燈號轉紅並寫出是哪個
  commit 還原的；已經完成的卡會回到「需要你」，並通知當初交辦的 Bot 一次。
- **手動改掉、或還原時解過衝突的，系統認不出來**。這種要由 Bot 或你記一筆「這個 commit 還原了
  那個」，系統標明這是人說的。
- 系統不會自己把卡片重開或關掉：還原有可能正是你要的，這由你決定。
- 綠燈的意思是「某時某刻驗證過，到當時為止沒發現被還原」，滑過去看得到驗證到哪個版本。
- 一張卡刻意取代另一張時，新卡審查通過後可以記一筆「取代」，舊卡變灰並標明被誰取代，由你收尾。

## 它會替你擋什麼

被退回、而且之後沒有被取代的 commit，推送到遠端時會被擋下，並說明是哪張卡、誰退回的；
Clawdline 專案另外在裝開發版和部署 Cloud 時也擋。系統查不清楚時也會擋。合併到本機主線不擋
（還能收回），但燈號會變紅並告訴整合的 Bot。

- **退回的範圍不會誤傷別人**：開發的 Bot 如果為了跟上進度把主線合進自己的分支，那些早就在
  主線上的 commit 不算在退回範圍內。這一點會有專門的測試。
- **在主線上把被退回的 commit 乾淨還原，就不再擋**；系統自己看得出來。
- 只有你能放行被退回的 commit，要寫理由。Bot 沒有任何方式自己放行。
- **其他專案**：系統不會去改別的專案的推送檢查或部署腳本。你可以自己加一行指令啟用；
  沒加之前，那個專案只有「事後發現並警告」，沒有「事前擋下」，卡片上會寫明。

老實說兩個限制：推送前的檢查可以被刻意跳過；被退回的修改如果被壓進別的 commit，系統認不出來。
所以系統另外會持續核對遠端和各個去處，一旦發現被退回的東西已經上去，就把卡片標成「需要你」
並通知你。

## 什麼時候算完成

這張卡需要的去處全部驗證過、沒有被還原或被取代，系統就自己把它標成完成，並通知當初交辦的
Bot（只通知一次，重開機也不會重複）。哪些去處是必要的，可以每張卡不同，例如只改文件的卡不必上
Cloud。Bot 不能自己宣布完成；你可以手動完成或取消。

## 上線後驗收（可選）

去處的燈只說明「含有這個 commit 的版本已經在跑」，不代表功能在上面真的正常。團隊現在已經有
測試的 Bot 上線後去看一眼（例如截圖檢查），只是也還寫在聊天裡。提案把它做成**可選的第四個
角色「驗收」，預設關閉**：需要驗收的卡，去處驗證過後交給驗收的 Bot，它記下通過或不通過，
並綁定當時線上實際的版本；不通過就退回給開發的 Bot。驗收結果是 Bot 的說法，系統讀不了截圖，
所以會標明是誰驗收的，不會畫成一個「已驗證」的燈。

## 卡片從哪裡來

你交代 Bot 一件**會改到程式或文件**的事，Bot 第一次派出要寫檔的工作時，系統就自動開卡。
只是問問題、做調查不會開卡。同一則訊息不管經過幾位 Bot、重試幾次，都只會有一張卡。

## 刻意不做的

- 不幫你排誰來審查，也不替 Bot 跑建置、推送或部署。
- 不處理從別台電腦的 Bot 網路送來的請求。
- 不涵蓋公開版發布與官網（之後可以用「專案自己定義的去處」加進來）。
- 不改動看板項目，也不放進看板的數字。
- 不讓 Bot 定義去處，也不讓去處用「跑一段指令、相信它印出的結果」來判定。
- 不去安裝或修改其他專案的推送檢查與部署腳本。
- 不會因為還原或取代就自動重開、關閉卡片。
- 一個整合批次不跨專案、不跨分支。

## 需要你決定的事

前八題是第一版的問題；第 4 題因為去處改成各專案自己定義而調整了說法。第 9、10 題是這一版新增的。

1. 看板的「Bot 工作」區要**預設顯示**，還是像「Agent 提案」一樣**預設隱藏**、勾選才顯示？
2. 需要你處理的 Bot 工作卡，要不要也出現在看板的「需要處理」欄？（會讓兩種紀錄在那一欄混在一起；
   不放的話，只在 Bot 工作區、Bot 聊天室和通知裡出現。）
3. 一則訊息裡交代了好幾件不相干的事，開一張卡就好，還是讓 Bot 拆成幾張？
4. 新卡預設要求哪些去處：這個專案有的全部都要，還是主線和遠端必要、專案自己的去處
   （Clawdline 是開發版和 Cloud）由開卡的 Bot 依內容決定？
5. 推送前的檢查可以被刻意跳過，搭配「發現已上線就警告」夠不夠？還是要求所有推送都改走
   Clawdline 的指令（改動比較大，Bot 的習慣也要跟著改）？
6. 被退回的修改如果被複製成新的 commit，要不要也認得出來？（推送前的檢查會稍微慢一點。）
7. 卡片完成時，只通知交辦的 Bot，還是也通知你？
8. 「有條件通過」要不要也擋推送和部署，直到整合的 Bot 說明條件已經達成？還是只顯示出來？
9. 功能被壓成一個 commit 或手動合併、系統無法證明落地的就是審查過的內容時，要不要規定審查的
   Bot 必須對實際落地的 commit 再通過一次，卡片才能完成（每次壓縮多一道審查）？還是整合的 Bot
   說了、畫面標明「聲稱」就夠？
10. 第一版要不要就包含可選的「上線後驗收」步驟（測試的 Bot 在線上確認後卡片才完成，記為該 Bot
    的說法）？還是等其他部分用起來再加？
